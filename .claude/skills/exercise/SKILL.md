盤面に仕事が無いとき、仕事を探すのではなく**作戦を回す**。運用すれば必ずどこかで詰まり、**その詰まりが次に作るものの唯一信頼できる情報源**になる。機能一覧を眺めても、要望を聞いても、同じものは出てこない。

監査ではなく**使用**だから効く。「Initiative 画面に何が足りないか」を検討しても出てこないが、燃料供給網が途絶して指揮官が決断を迫られた瞬間に「決断を書く場所が無い」ことは避けようがなく分かる。そして機能を入れると、その機能を使ったときにしか見えない次の摩擦が出る —— この連鎖が駆動の本体。

実装ループ（盤面から取って PR にしてマージするまで）は [friction](../friction/SKILL.md)。こちらはその**上流**、盤面に何を載せるかを決める側。

## 演習の設計

**盤面に実データとして作る。** Domain 1つ、Phase を数個、Object 4〜6、Element 8〜16、Worker は架空の人物。すべて description に `【架空演習】` と明記する。生 SQL で作るときの罠は [friction/references/db.md](../friction/references/db.md)。

- **前の演習の AAR が名指しした未解決の類型を狙う。** 思いつきで作らない
- **危機を仕込む。** 順調な計画は何も暴かない。**明示した前提を途中で壊す**のが最も効く
- **制約の種類を変える。** 軍事シナリオでは物資と時間が、企業シナリオでは人が制約になる。同じ機能が違う壊れ方をして、同じ症状のより深い原因が見える
- **小さく保つ。** 大きくすると演習の維持自体が仕事になり、観察が薄くなる
- **Initiative の description に「崩れたら知りたい前提」を明示する。** 後でそれを壊すため

## 1サイクルの形

**再演 → 進行 → 観察 → 疑問 → 仮説 → フィードバック。** 飛ばさない。

0. **再演** — 前のサイクル以降にマージされた所見があれば、それを生んだ状況をもう一度やる（下の節）
1. **進行** — 作戦を1日分または1週分進める。status と progress を動かし、コメントで何が起きたかを書く。ここで手を抜くと観察が出ない
2. **観察** — 盤面を**実際に見て**、何が見えて何が見えないかを書く。SQL で数えられるものは数える。「見えるはずのものが見えない」は数字で示す
3. **疑問** — 下の節
4. **仮説** — どう直すか。**既存の設計を先に読む。** 「機能が無い」と感じた箇所に実装があり呼び出し元だけが無かった例が 25 件中 8 件あった
5. **フィードバック** — 所見を Element として起票し、SITREP を Initiative のコメントに出す

## 問いはどこから来るか

好奇心を持てという指示では出ない。**目的・基準・出力形式の3つ**で機械的に作る。

**① 目的が先にある。** 隙間は目的があって初めて見える。演習が供給しているのはこの目的であって、ネタではない。

**② 基準は製品自身の宣言。** [CLAUDE.md](../../CLAUDE.md) の概念モデルが何を意味すると宣言しているかを読み、実装がその宣言を守っているかを突き合わせる。良い問いは全部この形をしている —— 「Phase は**時間箱**と宣言されているのに、箱が閉じるときに中身をどうするかが定義されていない。それは時間箱ではなく永久のラベルでは？」。外から評価軸を持ち込まず、**製品が自分で名乗った意味を実装に突きつけているだけ**なので、誰でも回せる。

**③ 出力形式を縛る。** 「これが足りない」を禁じ、「なぜ〜なのか」の形を強制する。

**なぜ問いでなければならないか。** 診断が間違っていても問いは生き延びるが、要望は生き延びない。「作ってください」で終わっていたら、既にあることに気づかないまま二重に作っていた。

## 再演 — 直ったかを、直した人以外が確かめる

所見が実装されてマージされたら、**次のサイクルの冒頭でその状況をもう一度やる**。無いと検証が偶然になる。

**再演する側には、元の観察だけを渡す。PR の説明も、実装者が書いた理由も、コミットメッセージも渡さない。** 理由を読んでからの確認は必ず「なるほど直っている」に倒れる。渡すのは Element の `## 観察` 節と、動いている盤面だけ。独立エージェントに委任するのが理想だが、同じセッションが続けてやる場合も**先に PR を読まない**規律は同じ。

Element にコメントで4択と一行の根拠を出す。

| | 意味 |
|---|---|
| `◎ 解消` | 同じ状況をやって、摩擦が無かった |
| `○ 部分的` | 楽にはなったが手数が要る。**何が残っているかを書く** |
| `△ 未解消` | **実装が的外れだったのか、所見の診断が違ったのかを分けて書く** |
| `＋ 別の摩擦` | 元の摩擦は消えたが次が出た。**その場で新しい Element を起票する** |

`＋ 別の摩擦` が一番価値が高い。

**判定は受け入れ条件に対して行う。PR のスコープに対してではない。** 実装が指示どおりでも受け入れ条件が満たされていないことがあり、差はブリーフに出る。**ブリーフを自分が見つけた症状から書かない。Element の受け入れ条件から書く。**

**かけすぎない。** 実装まで到達した所見にだけかけ、**次のサイクルの進行に相乗りさせる**。全件に形式的な再演を課すと、演習が手続きになって観察が痩せる。

## 所見の質を盤面から読む

印象で語らない。**どれも良し悪しの断定には使えない** —— 見方を変える材料として読む。

- **実装到達率** — 低くても悪いとは限らない（判断待ちで正しく止まっていることがある）。ただし**理由なく滞留している**なら受け入れ条件が曖昧だった可能性が高い
- **「既に作ってあった」率** — 高いなら仮説の前に既存設計を読む手順を飛ばしている
- **訂正の回数** — **0 は良い数字ではない。** 気づいていないか隠している可能性を疑う

## 所見の起票

**摩擦を感じたその場で Element にする。** 後でまとめない —— 忘れるからではなく、**痛みの文脈が失われる**から。

description の型：`## 観察`（何が起きて、盤面が何を見せ、何を見せなかったか。数字を入れる）/ `## 疑問`（なぜそうなっているのか。要望ではなく問い）/ `## 既にあるもの`（関連する既存のテーブル・関数・コンポーネント）/ `## 仮説`（最小案を必ず含める）/ `## 受け入れ条件` / `## 注意`（削除するな・自動化するな等）。

`direction` にも `approach` / `acceptance` / `next` を入れる。起票先の Object は内容で選ぶ。

## SITREP と AAR

**SITREP** は毎サイクル Initiative のコメントに出す。作戦の状況が前半、`--- Friction 運用所見 ---` 以下が後半。**ユーザーは Initiative を見ているだけで全体が追える**のが狙い。`mentions` に判断を仰ぐ user の uuid を入れる。

**AAR** は演習の終わりに1本。作戦の結果、所見の一覧、**分かったことの類型化**、**次の演習が狙うべき類型**。次の演習の設計はここから始まる。

## セッションをまたいで続ける

**演習の状態は盤面にある。** このファイルにも記憶にも無い。

```sql
-- ① 走っている演習
select id, name, identifier, description from domains
where description like '%架空演習%' order by created_at desc;
-- ② その演習の Initiative（scope の domain_ids に ① の id）
select id, name, description from strategies order by created_at desc;
-- ③ 最後の SITREP（strategy_id で必ず絞る。名前の like は Alcon 自身の Initiative を拾う）
select author_name, content, created_at from strategy_comments
where strategy_id = '<② の id>' order by created_at desc limit 3;
-- ④ 作戦の現在地
select e.display_id, e.title, e.status, e.progress, p.name as phase
from elements e join objects o on o.id = e.object_id
left join phases p on p.id = e.phase_id
where o.domain_id = '<① の id>' order by e.display_id;
```

最後の SITREP を読めば、どのサイクルまで進んだか・何を観察済みか・何を起票済みかが分かる。AAR が出ていれば演習は終わっているので、AAR が名指しした類型で次を設計する。演習が1つも無ければ直近の AAR を探し、それも無ければ未着手 Element から痛そうな類型を1つ選ぶ。

## 規律

- **確かめられることを推測しない。** **最初に触った道具の反応は、システムの性質ではない。** 数える・引く・実際に流す手段があるならそうする
- **間違えたら盤面に証拠つきで訂正を書く。** 取り消して黙らない。**次のセッションが読むのは盤面であって、こちらの反省ではない**
- **委任先が申告した妥協と推測を、そのまま盤面に残す。** ブリーフ品質の検証データであり、隠すと次の委任も同じ穴を踏む
- **止まらない。** 判断が要るものはユーザーに上げつつ、要さない Element を先に消化する。ブロッカー自体も Element にする
- **演習で作ったデータは消さない。** 次の演習との比較材料であり AAR の根拠

起票された Element を実際に作るのは friction の領分。演習側は観察して起票するところまで —— ただし同じセッションが続けて実装してよく、その場合は friction の規約に従う。
