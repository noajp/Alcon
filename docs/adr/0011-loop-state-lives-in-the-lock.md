# 0011. ループの状態はロックファイルに置き、レポートは盤面に置く

2026-08-31 / el_OPS-026

## 背景

ADR 0009 は SessionStart hook でループを起動し、リースで1つに絞った。起動は解決したが、その ADR 自身が「覆す条件」の筆頭にこう書いていた——**hook が保証するのは「プロセスが動いていること」までで、「人が気づけること」ではない。**

実測すると、そこはもっと悪かった。`board-listen` は起動時にも join 成功時にも何も出さず、`stall-check` は健全なとき無出力であることが設計。**両方のログが 0 バイトで、それが「盤面が静か」なのか「realtime に join できていない」のか「そもそも死んでいる」のかを区別できない。**

WebSocket が開くことと購読が成立することは別で、join に失敗したソケットは開いたまま何も運ばない。これは「誰も働いていない盤面」と完全に同じ見え方をする。

同時にファイル側も壊れていた。ログは hook のシェルリダイレクト（`>>`）で書かれていて、**誰も所有していない**。上限なく育ち、書いたプロセスが死んでも残る。実測で、前日のプロセスが残した 0 バイトのログが2本、誰にも回収されずに残っていた。

## 選択肢

1. 通知経路を作り直す（各セッションが Monitor でログを追う）
2. 生存状態を DB に置く（`dev_control` に列を足す、あるいは専用テーブル）
3. 生存状態を、プロセスが既に所有しているロックファイルに置く
4. 起動時に1行出させるだけにする

## 決定

3。加えて**ログの所有権をプロセスに移し**、活動レポートは**盤面（Campaign）に置く**。

`board-listen` は realtime の join 応答を受けた時点で `state: listening` と `joinedAt` をロックに書き、切断時は `reconnecting` に落とす。`stall-check` は毎 tick `clear` / `N stalled` を書く。どちらも60秒ごとに `seenAt` を更新する。

`ops/loop-report.mjs` がそれを読み、盤面の動きと合わせて1枚にする。`--post` で Campaign にコメントとして投稿する。

## 根拠

1 を捨てたのは、**あなたが全セッションに通知を飛ばしたくないから**。ADR 0009 は「気づけない」を通知の問題として立てたが、実際に足りないのは通知ではなく**問い合わせられる状態**だった。ループは裏で静かに回っているのが正しく、必要なときに訊けることの方が価値が高い。リースが1セッションに絞っている以上、通知経路を増やせば絞った意味が消える。

2 を捨てたのは、**「ループは起きているか」が migration を要する質問であってはならない**から。加えて DB に置くと、DB に到達できないときに「ループが死んだ」と「DB が死んだ」が同じ無回答になる。ロックはローカルなので、この2つを切り分けられる。

3 を選んだのは、置き場所が**既にある**から。ロックファイルは既に作られ、既にスコープが正しく（リポジトリ単位）、既にプロセス終了時に片付けられている。生存情報はまさにその寿命を持つ。新しいファイルもテーブルも増えない。

4 では足りない。起動時の1行は「起動した」しか言わず、**その後死んだことを言えない**。`seenAt` が止まることだけが、死を沈黙と区別する。

書き込みを `link` の儀式ではなく in-place にしたのは、排他はその時点で決着済みだから。再 link するには自分のロックを一度 unlink する必要があり、そこが競合する起動者に奪われる唯一の窓になる。**破れた読み取りは呼び出し側のポーリング1回分の損、失ったロックはループの排他そのものの損。**

ログの所有権を移したのは、シェルリダイレクトには所有者がいないから。プロセスが持てば、起動時に切り詰め、稼働中に上限を守り、**正常終了時に自分で消せる**。残るログは書き手がクラッシュしたものだけになり、それは**ログが読む価値を持つ唯一のケース**でもある。

レポートを盤面に置くのは、**バックログの単一情報源は盤面**という前提の帰結。Campaign は「この努力が何をしているか」を俯瞰する層で、プロトコルは既にふりかえりを Campaign に残せと言っている。ファイルに書けば、誰も更新しない第二の情報源が増える。

## 覆す条件

- **ロックが置かれる tmp がセッションをまたいで消えるようになったとき。** 今は macOS の `TMPDIR` がログイン中は保たれる前提。OS の掃除周期がプロセス寿命より短くなれば、生存記録は別の場所が要る
- **リポジトリ1つにリスナー1つでは足りなくなったとき。** ドメインごとに別の盤面を見る使い方が出れば、ロックのキーと同じくレポートの粒度も変わる
- **人ではなく機械がレポートを読むようになったとき。** 今の出力は人が読む Markdown。ディスパッチャが判断に使い始めたら、構造化された形が要る
- **無人稼働が要件になったとき。** hook はセッションが1つも開かれなければ何も起こさない。ADR 0005 と 0009 と同じ条件でクラウド routine に置き換わる
