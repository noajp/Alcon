# 0044 — AI の監査台帳は書類を持たずに記録を持ち、鎖で改ざんを示す

## 背景

AI エージェントが顧客の業務（受注の転記、請求書の受領など）を外部の実行基盤で代行するとき、経営者や管理部門は「何を任せ、何が行われ、人がどこで判断したか」を確かめたい。一方で、取引書類の中身を Alcon に置くと、漏えいの影響と保管の責任が増え、「書類を保存しない」という導入時の約束が成り立たなくなる。記録は監査に使うので、書いた本人を含め、誰も後から書き換えられないことを示す必要もある。

Alcon の `agent_runs.transcript` は会話の本文を保存する。外部の実行基盤の記録に、この形は使えない。

## 選択肢

1. `agent_runs` / `agent_actions` を拡張し、外部の実行も同じ表に入れる
2. 外部の実行は別の台帳に分け、書類は番号と鍵つきダイジェストだけを持つ。実行の結果は手順のイベントとして追記する
3. 記録は顧客のストレージにだけ置き、Alcon は表示のたびに取りに行く

## 決定

2 を採る。

- `workflow_templates`（業務の定義・版・目的・手順）、`workflow_deployments`（Space で動く導入：Domain・例外の Object・ai_agent の Worker・状態・1件あたりの想定作業時間）、`workflow_runs`（1件の書類に対する1回の実行）、`workflow_run_steps`（関節で起きたこと：接続・操作・結果・実行者）
- 実行の結果は保存せず、手順から読む（`runOutcome`）。台帳を追記だけにでき、読み方を変えても過去を書き換えずに済む
- 実行と手順は、service role を含むすべての書き手に対して UPDATE / DELETE / TRUNCATE を権限で外し、トリガでも拒む。例外は Space の削除によるカスケードだけで、導入の直接の削除も拒む
- 手順は導入ごとに1本のハッシュの鎖を作る。挿入時に DB が `seq`・前の行のハッシュ・自分のハッシュを計算し、導入の行をロックして並行書き込みを直列にする。ハッシュは手順と、その手順が属する実行（書類番号・ダイジェスト・開始時刻）を覆い、各項目をバイト長つきで連結して境界をずらせないようにする。`Function/audit/auditModel.ts` の `verifyChain` が同じ形で検証する
- 実行・手順の Space と導入は、書き手の申告ではなく親の行から決める。導入の Domain・Object・Worker は同じ Space のものに限り、テンプレートは同じ業務の別の版にだけ移せる
- 読み取りは導入が属する Space のメンバーで、導入に Domain があるときはその Domain を見られる人に限る。導入が使っている Domain は削除できない（削除すると閲覧範囲が Space 全体に広がるため）。書き込みは記録の受け口（service role）だけが行う
- 画面は実行の一覧を `audit_ledger_runs` で1回に読み、結果は1つの JSON 値で受け取る。1つのスナップショットなので、受け口が追記を続けていても件数のずれで失敗しない。行の集合で返すと API の行数上限で黙って切られるため、上限を超えたかどうかは関数が自分で返す。直近30日の実行（新しい順に上限まで）に加え、それより前でも終わっていない実行は上限とは別枠で必ず含める。閲覧の判定は導入ごとに1回行う
- 終わっていない実行は、人が判断した結果を実行基盤が end の手順として書き足したときに閉じる。Alcon は実行の行を書き換えて閉じない
- 鎖の検証は、導入ごとに seq が連続する最新の範囲を別に読んで行い、同じ要求で全件数も受け取る。期間の窓で手順を切ると鎖が歯抜けになり、改ざんがないのに切れて見えるため。調べたのが一部なら「最新 n 件」と書き、全体が健全だとは言わない
- 画面は Sustainment の App「Audit」とし、ほかの画面と同じ型で組む。最初に開くのは概況（PageHead・人の対応待ち・ワークフローの一覧と Properties）、ワークフローは ToolPage のタブ（概況・実行・流れ・記録の完全性）、監査ログは全件と人の対応待ちのタブ。行き先はサイドバーだけに置き、タブと重ねない
- 見られる導入がない間は、架空の2つのワークフローを画面の中だけで見せる。サンプルは DB に書かず（追記のみの台帳に入れると取り消せないため）、見られる導入が登録された時点で消える。閲覧範囲の外にしか導入がない人にも出るので、案内は「あなたが見られるワークフローがない」と言い、Space に導入がないとは言わない。サンプルの記録も DB と同じ方法で鎖にし、同じ検証で確かめる

## 根拠

- 1 は、本文を持つ表と持たない表の約束が混ざり、RLS も Element の可視性に縛られる。外部の業務は Element を持たない実行が大半で、合わない
- 3 は、顧客ごとのストレージ形式に表示が依存し、集計（自動完了率・差し戻し率）が遅く脆くなる。記録はメタデータだけなので Alcon に置き、求める顧客には同時に書き出す形で補える
- 鎖を DB で計算すれば、受け口や実行基盤の実装に関わらず、抜けや書き換えが鎖の切れ目として残る。画面で検証できるので、「記録がある」だけでなく「記録が欠けていない」を示せる

## 覆す条件

- 顧客が記録を自社の外に置くこと自体を拒む場合 → 3 に寄せ、Alcon は集計値だけを持つ
- 導入あたりの手順が多く、導入の行のロックが書き込みの待ちを生む場合 → 鎖を導入×日などの区間に分け、区間の先頭で前の区間の末尾を参照する
- 外部の実行と Alcon 内のエージェント（`run-agent`）を同じ画面で監査する必要が出た場合 → `agent_runs` を本文なしの形でこの台帳に写すか、両方を読む表示に広げる
- Space の実行が増え、`audit_ledger_runs` の応答が重くなった場合（終わっていない実行の判定は Space の全実行をたどる）→ 集計を DB 側に移し、画面には件数と最新の実行だけを返す
- 追記のみを守る仕組みは、DDL の権限を持つ者（トリガを作り替えられる者）には破れる。それを防ぐ必要が出た場合 → 鎖の末尾のハッシュを定期的に外部（顧客のストレージなど）へ書き出し、外から照合できるようにする
