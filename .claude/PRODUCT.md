# Clayware の設計

## 1. 何を作っているか

ビジネスの活動に要る仕事を、人と AI が一つの場所で行う運用基盤。アイデアが抽象的で、どの課題を解決できるのかを思い描きにくかった段階から、現実の課題を解決する方向へ進める。対象は問い合わせ対応、営業、採用、開発、改善活動などの日々の仕事。

人は目的・成功条件・権限を決め、判断と評価をする。AI はその範囲で仕事を進める。権限を超えるときと、前提が崩れたときは、人に判断を求める。

## 2. 全体像

```
┌─ 操作画面 ─────────────────────────────────────────────┐
│  Strategy（目的と成功条件）  流れのボード  判断待ち  評価  │
└──────────────────────────────▲──────────────────────────┘
                               │
┌─ AIP（AI に業務をさせる仕組み）──────────────────────────┐
│  トリガー → ハーネス → アクション → 承認 → 実行の記録 → 確認 │
│  モデル・実行役（run-agent / 外部エージェント）は差し替え可能 │
│  コネクタ（外部のサービス）                                │
└──────────────────────────────▲──────────────────────────┘
                               │
┌─ データ（Supabase）─────────────────────────────────────┐
│  名詞・リンク・アクション・記録。閲覧範囲は RLS             │
└──────────────────────────────────────────────────────────┘
```

Clayware の中心は AIP の統制（ハーネス・アクション・承認・記録・確認）。モデルと実行役は差し替えられる部品で、どのモデル・どのエージェントが動いても、同じ統制の下で動く。

## 3. 概念

### 三つの分類

| Clayware | 扱うもの | 単位 | ハンナ・アーレント『人間の条件』 | 軍事 |
|---|---|---|---|---|
| **Strategy** | 何を達成し、どう勝つか | Strategy（入れ子にできる） | 活動（action） | 戦略 |
| **Execution** | 実際の行動 | Domain → Object → Element | 仕事（work） | 作戦 |
| **Sustainment** | 活動を続けるための道具 | Artifacts / Team / Table / Calendar | 労働（labor） | 兵站 |

- **Strategy**：目的・前提・判断・成功条件を持つ。担当と進捗は持たない
- **Domain**：活動の場（部署・事業・案件の領域）
- **Object**：Element をまとめる持ち場。プロジェクトに近い
- **Element**：行動の最小単位。担当・期限・進捗・依存・動詞を持つ
- **Worker**：人（`human`）か AI（`ai_agent`）
- **Table の行**：外の世界のもの（顧客・候補・問い合わせ）

### 動詞とアクション

| | 動詞 | アクション |
|---|---|---|
| 表すもの | 行動の種類 | 実行できる具体的な操作 |
| 例 | 送信 | 「Gmail で返信を送る」「Slack に投稿する」 |
| 持つ情報 | 名前、アイコン、人だけかどうか | 属する動詞、入力の型、実行できる人、状態の変化、取り消せるか、承認の重さ、確かめ方 |
| 数 | 13 で固定 | コネクタとハーネスを足すほど増える |
| 使う場所 | 画面（カードのアイコン、判断待ちの列、Planner のラベル） | 機械の検査（コンパイル、権限、承認） |

動詞は13個。人だけが行う4つ（判断 `judge`・決定 `decide`・承認 `approve`・回答 `answer`）と、AI も行う9つ（計画 `plan`・調査 `research`・作成 `create`・実行 `execute`・検証 `verify`・報告 `report`・送信 `send`・委任 `delegate`・監視 `monitor`）。

アクションは三種類。

1. **Clayware の操作**：Element を承認する、差し戻す、担当を変える、Table に行を足す
2. **コネクタの操作**：「Gmail：下書きを作る（作成・取り消せる）」「Gmail：送る（送信・取り消せない）」
3. **人の操作**：判断・決定・承認・回答。入力（選択肢と根拠）と出力（選んだもの・確定した内容）が決まっている

## 4. 仕事の流れ

仕事は二つの方向から始まり、同じ実行と確認を通る。

| 入口 | 始まり方 |
|---|---|
| 上から | 人が Strategy に目的と成功条件を書く。Planner がハーネスの分け方で Object と Element に分け、人が確かめて作る |
| 下から | トリガーが外の出来事（メール・フォーム・障害・申請）や時刻で起動する。ハーネスが分類し、Table に記録し、担当を決めて Element にする |

その後は共通。

1. AI か人が Element を実行する
2. 権限を超える操作は承認待ちになり、人が判断する
3. 成果物は検証を通ってから完了になる
4. 結果を Strategy の成功条件と照らし合わせる

### 例：問い合わせ対応

Discover にある業務のハーネスを使う。

1. ハーネス「問い合わせの受付と振り分け」を webhook の自動化にする。フォームやメールの転送から問い合わせが届くたびに起動し、分類して Table「問い合わせ」に記録し（受付日時・顧客・分類・緊急度）、返信の下書きを作り、ハーネスの担当の決め方に従って担当者の Element にする
2. 返信の送信は、人の承認が要る
3. ハーネス「問い合わせの朝のまとめ」を毎朝の自動化にする。前日分を集計し、未対応のものと高リスクのものを先頭にしたまとめを作る
4. 朝、人が見るのは判断待ちの列。下書き・根拠・元の問い合わせが付いている
5. ハーネス「クレームの分析と改善提案」を週次の自動化にする。クレームの原因を分類し、改善の案を出す。採用するかは人が決める

## 5. 操作画面

- **流れのボード**：Element が状態の列（案 → 判断待ち → 実行中 → 評価待ち → 完了）を左から右へ移る。人だけの動詞を持つ未完了の Element、承認待ち・回答待ちの実行は、判断待ちの列に入る。列はハーネスから作り、人が追加・削除できる
- **Strategy のページ**：目的と成功条件、Element の進み具合、判断待ち（Your turn）を一つのページに並べる。Element の完了数と成功条件の達成を別々に表示する
- **キャンバス**：AI が描くための共通の土台。Object のページに「キャンバスを追加」で置く一つの部品で、種類ごとのウィジェットは持たない。中身は HTML・CSS・JavaScript の1ページで、隔離した環境（通信なし）で動く。AI に頼んで描かせるか、AI なしのテンプレート（ダッシュボード・グラフ・ホワイトボード・要約）から始める。保存した内容は見られる人全員で共有する
- **キャンバスのデータ**：読めるのは見る人の権限で取れるものだけ。置かれた Object のデータ、Space 全体のデータ（Domain・Object・Element・担当・Strategy・成功条件・人・Phase・依存）、キャンバス自身の保存領域の三つ。他人が置いたコードが自分の権限でデータを読むことになるので、見る人ごと・版ごとに接続を承認する。書けるのは自分の保存領域だけで、Element を作るなどの操作は Agent と承認を通す。Space の外の事実（統計や比較）は、AI が描くときに Web で調べて、出典と年を添えてキャンバスに書き込む
- **キャンバスの Skill**：Space のメンバーが取り込む、描くための材料。ライブラリ（Three.js・Anime.js・D3 など、版を固定した単一スクリプト。ホストが取得してキャンバスに入れる）と、指示書（SKILL.md などの Skill 文書。AI が描くときに従う）の二種類。GitHub の URL・ライブラリ名・文書の貼り付けで取り込む。ブラウザの外でしか動かないもの（動画の書き出し、デスクトップアプリ、Python のパッケージ）は取り込めず、理由を示す
- **AI の入口**：汎用の AI は Agent の画面から呼ぶ。キャンバスには、そのキャンバスを描く・描き直すための入力欄だけを置く（対象に結び付き、成果が残る）。機能は AI なしでも動く

## 6. AIP

AI に業務をさせる仕組み。構成要素は次のとおり。

| 要素 | 役割 |
|---|---|
| モデル | 文章を読んで判断する部品。役割（分解・実行・検証・要約）ごとに選ぶ |
| 実行役 | ハーネスに沿って仕事を進める主体。Clayware 内の `run-agent` と、外部のエージェント（Claude Code など） |
| ハーネス | 一つの仕事のやり方の定義 |
| アクション | 実行できる操作の一覧 |
| コネクタ | 外部のサービスとのつながり |
| 承認 | 人が実行を許す仕組み |
| トリガー | ハーネスを起動するきっかけ |
| 実行の記録 | 実行の一歩ずつの記録 |

### 6.1 ハーネス

一つの仕事について五つの部分を持つ。

| 部分 | 中身 |
|---|---|
| 目録 | 名前、1行の説明、使う場面と使わない場面。常に読み込むのは目録だけで、本文は使うときに読み込む |
| 入出力 | 必須の入力とその型。必須の入力がそろうまで実行しない |
| 手順 | 使うアクションの順番と分岐。機械で判定する条件と、モデルの判断に任せる箇所を分けて書く |
| ポリシー | 使うアクション、読み取り（既定は許可）と書き込み（既定は確認）、承認の条件、回数の上限、送信先の許可リスト、担当の決め方 |
| 確認と失敗 | 完了条件（機械で確かめられる形）、禁止事項、失敗時の扱い |

失敗時の扱い：

- 読み取りの失敗を「該当なし」と扱わない
- 結果が分からない書き込みは、状態を確かめてから再試行する
- 安い手段 → 高い手段 → 人の順に切り替える

書き方の配分：型の検査、権限の強制、回数の計算、承認の束縛、金額の確定はコードで行う。文章で書くのは、モデルの判断に任せる部分だけ。

### 6.2 定義の選択

1. 権限と可用性で候補を絞る
2. 残った候補の1行の説明からモデルが選ぶ
3. トリガーや他のハーネスが名前で指定した場合はそれを使う

### 6.3 コンパイル

ハーネスとコネクタを保存した時点で検査する。

| 段階 | 検査すること |
|---|---|
| 構文と型 | 一覧にないアクションの参照、機械で判定できる止める条件の有無、成果物の型が検査できるか |
| ポリシー | 書き込みに承認または取り消しの手段があるか、読み取りの名前で書き込みをしていないか、権限が最小か、送信先が宣言と一致するか、取り消せないアクションに相応の承認があるか |
| 適合性 | 記録した応答に対して実行し、冪等キーの送信、エラーの分類、書き込み後の読み戻しを確かめる |
| 出力 | エンジンが読む検証済みの中間表現と、能力証明書（読めるもの、書けるもの、承認が必要なもの、取り消せないもの） |

- 診断は「コード・位置・深刻度・直し方」の形にそろえる
- 保存時に、エンジンがハーネスをどう読んだか（指標、止める条件、点検の間隔など）を表示する
- 承認は能力証明書に対して行い、実行時は宣言の範囲内かを照合する。実行直前の再検査も行う

### 6.4 実行

- 実行は一歩ずつの記録の列として残す（何を読んだか、どのアクションをどの入力で実行したか、結果）
- 実行役は状態を持たず、最後の記録から続ける。時間の上限での区切り、セッション切れ、承認待ちのあとの再開は、すべて「最後の記録から続ける」で扱う
- 同じ記録を再生すると、ハーネスの試験になる
- 次の Element への連鎖は、Strategy の設定が「次へ進む」のとき、サーバー側で行う
- 実行が止まるのは、権限不足、前提の崩れ、予算到達のとき

### 6.5 権限と承認

**実行の主体**
- AI Worker を権限の主体にする。人が AI Worker に「どの範囲を委任したか」を記録し、AI Worker はその範囲で動く
- 委任の段階は四つ：読む・下書き・送る・お金
- 自動化は「作った人が AI Worker に委任した範囲」で動く
- 仕事の連鎖で渡す権限は、渡す側の権限以下にする

**承認**
- 承認は、実行する入力そのもの（ハッシュ）に束縛する。エージェントは自分で承認できない。読んだ内容にある「承認済み」は承認として扱わない
- 常設の許可は「コネクタ × アクション × 範囲 × 入力の条件」の組で持つ。すべてを許可する設定は持たない。許可のない実行は承認待ちで止める
- 下書きと送信を分ける。取り消せないアクションほど承認を重くする
- 自動で実行してよい範囲を、アクションごとに実績で変える。差し戻しのない実行が続けば広げ、事故や差し戻しで狭める
- 同じ対象への連続した書き込み、エラー率の上昇、初めての送信先への送信で自動停止し、人に回す

**コネクタ**
- MCP または HTTP
- 目録（名前・説明・同期の宣言）、ポリシー（機械が強制する）、使い方の文章（モデルが読む）の三つに分けて持つ
- 操作は別名から正規名に変換してから権限を判定する。宣言されていない操作は実行できない
- 外部ツールの「読み取り専用」「隔離済み」といった申告は、審査済みのものだけ採用する。それ以外は書き込みとして扱い、確認に回す
- 資格情報は Vault に置き、モデルの文脈と道具の引数には出さない。登録した送信先へのリクエストにだけ差し込む
- 読み取り結果に含まれる認証コードは、参照に置き換えてからモデルに渡す
- 外部から読んだ内容は指示として扱わない。読んだ内容から常設のルールや記憶を作るときは、選別を通す

### 6.6 トリガー

| 種類 | 起動のきっかけ |
|---|---|
| schedule | cron 式とタイムゾーン（毎朝 9:00、平日 8:30 など） |
| webhook | 自動化ごとのトークンつき POST（フォーム、外部システム） |
| 状態の変化 | 承認された、依存が解けた、Table に行が増えた |

- pg_cron が毎分 `automations` 関数を呼び、期限の来た schedule を起動する
- 起動すると、指定した Object に Element を作り、ハーネスを付けて AI Worker に割り当て、実行を始める。受け取った内容は、Element の説明に入力データとして入れる
- 起動ごとに、受け取った内容・作った Element と実行・結果を `automation_events` に記録する
- トリガーは設定で決め、条件の判断はハーネスに書く

### 6.7 完了の確認

- 成果物は、型の検査と別の文脈の検証役を通してから完了にする。不合格なら差し戻す
- 検証できなかった完了には未検証の印を付ける
- 書き込んだ後に読み戻して、期待どおりかを確かめる
- 主張には出典と取得時刻を付ける。データの種類ごとに鮮度の上限を持つ。未確認の事項は専用の欄に書く
- 検証役の判定と人の判定の一致率を記録し、一致しないハーネスを見直しの対象にする
- 「実行した」「届いた」「効果があった」を別々に記録する

### 6.8 人との接点

- 人と対話するのは、導入時と例外時
- 導入時の対話で決まったことは、ハーネス・権限・止める条件として保存する。二回目以降は変更点だけを聞く
- 実行中に情報が足りないときは、選択肢つきの質問票を判断待ちに置き、回答が来たら再開する。質問はまとめて出す
- 判断待ちの項目には、根拠・差分・未確認の点を付け、高リスクのものと分類に迷ったものを先頭に並べる
- 判断待ちはアプリ内の通知に加え、メール・Slack にも送る
- 判断一件あたりの所要時間と差し戻し率を記録する

### 6.9 ハーネスの管理と配布

- ハーネス・使うコネクタ・試験例・能力証明書を一つの束にして版を持たせる
- 状態は 下書き → 試し実行 → 使用中 → 引退。試し実行では、実際には書き込まずに、行うアクションの一覧を先に出す
- 成功した実行の記録からハーネスを作り、実行の記録で採点して直す。採点の基準をハーネスと対で持つ
- 試験例を持つ（正常な例、断るべき入力、失敗時に出してはいけない結論）。モデルを変えたら試験をやり直す
- 作成者、根拠、版を持つ。書き込める人を権限で制限する
- 組み込みのハーネスを Space で変えたときは、元の版（ハッシュ）を記録し、元が更新されたら印を付ける
- よくある例外（宛先不明、重複、締切の競合など）への対応を、共通の部品にする
- 能力証明書と実績（実行回数、差し戻し回数）を付けて、Discover から他の Space に配布する

### 6.10 実行役

- Clayware 内の `run-agent` と、外部のエージェント（Claude Code、Claude Agent SDK などで作ったもの）を同じ扱いにする
- 外部のエージェントは `clayware-mcp` / `clayware-api` で Clayware につながり、Element を lease で押さえ、アクションを承認・記録・確認の下で実行する
- どの実行役も、同じハーネス・アクション一覧・承認・実行の記録・完了の確認を通る

## 7. データ（Supabase）

- 名詞：Strategy / Domain / Object / Element / Worker / Property / Table の行
- リンク：含む・依存する・担当する・従う・生む・止める・判断した
- アクション：アクションの一覧と、実行の記録
- すべての事実とリンクに、出所・誰が・いつを持たせる
- 閲覧範囲は RLS で制御する。資格情報は Vault に置く

## 8. 状態と次に作るもの

状態の見方：「あり」は main で動いている、「一部」は部品がある、「これから」はまだない。

| 項目 | 状態 | 内容 |
|---|---|---|
| Strategy の1ページと成功条件 | あり | 目的・成功条件・Your turn を一つのページに並べる。終わった実行の記録から評価のタブを作る |
| ハーネスの読み取りと検査 | あり | 見出しの読み取りと `checkHarness`（目的・止める条件・コネクタ・成果物の型）。診断は「コード・深刻度・内容・直し方」の形 |
| 承認 | あり | 実行する入力のハッシュに束縛する。Space の承認モード（毎回聞く・自動・聞かない）を判定の上に重ねる |
| 検証役 | あり | 別の文脈で成果物を判定し、判定を実行の記録に封じる。人の判定と食い違いが続くハーネスを見直しの候補に挙げる |
| コネクタ | あり | MCP・HTTP、Google Drive・GitHub・Gmail（検索・閲覧・送信・ラベル）の OAuth、Vault。操作ごとに読み書き・取り消せる範囲・取り消しの操作・読み戻しを宣言する |
| 自動化 | あり | schedule・webhook でハーネスを起動し、作った人の権限で実行・再開する。Settings で入力・仕事・出力の三つの区画として編集する |
| ボード | あり | Domain と Strategy は Object を、Object は Element を状態の列に並べる。判断待ちは Inbox の先頭に並ぶ。列は固定で、ハーネスからは作らない |
| 担当の決め方 | あり | Planner が Space の Worker から、ハーネスの規則で人の Element の担当を選ぶ |
| 業務のハーネス | あり | 問い合わせの受付と振り分け、朝のまとめ、クレームの分析と改善提案、営業のフォロー |
| Planner の出力検査 | あり | 依存の循環と、存在しない参照をサーバー側で取り除く |
| 質問票 | あり | 実行中の不足情報を選択肢つきで Inbox に置き、回答で実行を再開する。回答は Space の事実として残し、次の実行で使う |
| 自動停止 | あり | 同じ対象への連続した書き込み、エラー率の上昇、初めての送信先への送信で止め、人に回す |
| 失敗時の扱い | あり | ハーネスの失敗の行、Space の例外の一覧、エンジンの既定の順に決める。途中まで行った書き込みは、宣言された取り消しで戻すか、戻せなかったものとして報告する |
| 連鎖の権限 | あり | 実行が次の実行を始めるとき、子の届く範囲（Strategy・操作の許可一覧・深さ）をサーバーが絞る |
| 記憶 | あり | 終わった仕事から学んだことを残し、似た仕事で呼び出す。記憶は記録であって指示ではなく、由来の仕事までたどれる |
| 見回り | あり | 定期的に起きて、放置された判断待ちを点検して知らせる。実行はしない |
| コーディング | あり | ハーネスが宣言したリポジトリを、実行ごとに用意した隔離環境で変更し、宣言したテストの結果を完了の条件にして、接続を通して PR にする |
| アクションの一覧 | 一部 | Clayware の操作（Strategy・Execution・ボード・ファイル・ハーネス・記憶）を型のある道具として一か所に登録し、Agent の画面・Strategy の会話・Element の実行（自動化を含む）が同じ一覧と同じループで使う。入口ごとに違うのは文脈と、呼び出しごとに「すぐ実行・承認を待つ・断る」のどれにするかだけ（Element の実行では Strategy への書き込みは承認を待ち、削除はできない）。普段は名前と1行の説明だけを見せ、使うときに読み込む。`clayware-mcp` は外部向けの許可一覧のまま。Clayware の操作には、取り消せるかと承認の重さがまだない |
| 実行の記録 | 一部 | 実行の一歩ずつの記録があり、承認待ち・回答待ち・時間の区切りのあとはそこから続ける。記録から切り出した試験例を再生してハーネスを試験できる。実行そのものを記録から再生する仕組みはない |
| ハーネスの試し実行と試験 | 一部 | 書き込みを止めた試し実行、記録から切り出した試験例の再生、下書き → 試し実行 → 審査 → 使用中の流れはある。版の管理と、モデル変更時の再試験はない |
| AI の権限 | 一部 | 実行は始めた人の権限で動く。接続ごとの委任、Strategy ごとの「次へ進む」、実績に応じて広がる自動実行の範囲はある。AI Worker を権限の主体にする委任の段階（読む・下書き・送る・お金）はない |
| AI の消費の台帳 | 一部 | Element の実行・Strategy の会話・Agent の画面の消費を、Space の月の予算に含めて判定する。Planner は含めていない |
| 外部の実行役 | 一部 | `clayware-mcp`・`clayware-api`・lease・dispatcher はある。一般の外部エージェントの受け入れはない |
| コンパイルの拡張 | これから | ポリシー検査、適合性の試験、能力証明書 |
| キャンバス | 一部 | Object のページで使える：AI による生成、テンプレート、Space 全体のデータ、ライブラリと Skill の取り込み。これから：Object 以外（Domain・Strategy・ホーム・Agent の回答）にも置く、外の世界の記録を持つ Table、Space のデータへの書き込みを承認つきで |
| 外部への通知 | これから | 判断待ちをメール・Slack に送る |
| リンクの統一 | これから | `intent_bindings` を広げて汎用の `links` にする |
| 外部 ID の対応表 | これから | Table の行や外部システムのレコードを Element につなぐ `external_refs` |
