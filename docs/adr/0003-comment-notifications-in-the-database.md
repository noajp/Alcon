# 0003. コメント通知を DB トリガで作る

2026-08-30 / el_TRJ-006・PR #195

## 背景

コメントが Inbox に届いていなかった。通知はアプリ内のコード経路でしか作られておらず、**その経路を通らない書き込み — API / MCP 経由でエージェントが打つコメント — は通知を生まなかった**。Element を開くまで誰も気づかない。

Friction Self-Build ではエージェントの進捗報告がコメントなので、これは「報告しても届かない」を意味する。

## 選択肢

1. アプリ側の通知作成をエージェントの書き込み経路にも足す
2. Edge Function を経由させ、そこで通知を作る
3. `element_comments` の INSERT トリガで DB が作る

## 決定

3。`notify_element_comment()` トリガ。受信者は、アサインされた Worker の背後にいるユーザー・Element のオーナー・その Element の Object が属する Domain のオーナー、から**コメント投稿者本人を除いたもの**。`security definer`、`search_path` 固定。

## 根拠

1 は「書き込み経路を増やすたびに通知を足す」ことになり、**足し忘れが必ず起きる**。実際そうやって壊れていた。2 は同じ問題を1階層下にずらすだけで、SQL 直挿入という一番使う経路が依然として素通りする。

トリガなら **「どこから書いても通知が出る」が構造的に保証される**。現在の経路も、まだ存在しない経路も同じ。

`security definer` が必要なのは、RLS 下では書き込んだロールが**他人向けの notifications 行を INSERT できない**ため。definer で関数オーナーとして走らせ、`search_path` を固定して探索経路の乗っ取りを塞ぐ。

「Domain オーナー」を受信者に含めたのは、**購読モデルが無いことへの現時点の代用**。本来は「この Element を見張りたい人」が購読すべきで、コンテナの責任者を機械的に入れるのは近似。近似だと分かった上で選んでいる。

## 覆す条件

- **購読モデル（watch / subscribe）が入ったとき。** そうなれば Domain オーナーの自動受信は過剰配信になるので、受信者の決め方はトリガから購読テーブルの参照に置き換わる。これは「いつか」ではなく、通知が煩いという声が出た時点で来る
- 通知の種類が増えて条件分岐が肥大したとき。トリガに業務ロジックが溜まり始めたら、DB は「イベントが起きた事実」だけを書き、配信先の決定は別の層に出す
- 一括操作（コメントの大量投入・移行）で通知が洪水になったとき。トリガは1行1通知なので、抑制が要るなら層を挟む必要がある
