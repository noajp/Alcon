# 0021. リースは RPC で取る — 散文は記録であって取得ではない。保持者は表示名ではなくセッショントークン

2026-09-06 / el_TRJ-012 → ELE_TRJ-016

## 背景

「▶ 着手 — branch: …」というコメントが着手の宣言であり、盤面の台帳でもあった。しかしそれは散文で、機械は何も強制していなかった。二つの事故がそこから出た。

- el_OPS-013 は `in_progress` のまま持ち主が判別できず、孤児と誤判定される一歩手前まで行った（ADR 0007）
- el_UXQ-009 は blocked に落とした後、保留理由（InlineAddRow の存在）が消えたのに誰も気づかず数日沈んだ。blocked を見張る仕組みが無かった

el_TRJ-012 で構造を入れた。`elements` に `claimed_by` / `claim_expires_at` / `branch`、`element_comments` に `holder`、`claim_element()` / `release_element()`、保持者のコメントで期限を延ばすトリガ、リース列への直接書き込みを拒否する BEFORE ガード。

そのレビューゲートで、最初の実装が排他になっていないことが実測で判明した。保持者を `author_name` で照合していたが、全セッションが `'Claude'` で書く。1つの文字列は1人分の保持者にしかならず、どのセッションも他のセッションの Element を「再取得」でき、他人の報告が死んだセッションのリースを延命していた。

## 選択肢

1. 散文の規約を強化する（▶ の書式を厳格化し、リスナーで検査する）
2. `author_name` をセッション固有にする（`Claude@…` で書き込む）
3. コメントに保持者トークンの列を持たせ、リースはその一致でだけ延びる。取得は RPC のみ
4. 部分 unique index で排他する

## 決定

3。**取得は `claim_element()` だけ**（UPDATE の WHERE が排他：空き・期限切れ・自分のいずれか）。**延長は `element_comments.holder = elements.claimed_by` のときだけ**。**保持者はセッショントークン**（`Claude@<worktree名>`、`ops/lease.mjs whoami`）であって表示名ではない。`author_name` は人が読む名前のまま据え置く。

リース列と `holder` への直接書き込みは BEFORE トリガで拒否し、RPC（SECURITY DEFINER = postgres）と service_role だけを通す。列レベル REVOKE は Supabase のテーブルレベル grant に負けて無効だったので、ガードは権限ではなくトリガに置いた。

ループが盤面に触る経路は `ops/lease.mjs` の1本（claim / comment / release）に集約し、friction スキルの着手・報告・完了・並行統制をこの語で書き直した。

## 根拠

- **散文は取得にならない。** 二人が同じ文を同時に書ける。排他は書いた事実からは生まれず、書く前に勝ち負けが決まる場所（1つの UPDATE）にしか置けない
- **表示名は保持者になれない。** 「誰が書いたか」と「誰が持っているか」は別の問いで、前者は人間が読むために同じ名前でよく、後者は機械が区別するために違う名前でなければならない。両方を1つの列に押し込んだのが最初の誤り
- **報告とリースの維持を同一の行為にする。** 新しい時計を足さない。停滞検知は既に進捗コメントをハートビートとして読んでいる。刻印付きのコメントが同時にリースを延ばすなら、守る規律は増えない —— 黙ったまま持ち続けることだけができなくなる
- **選択肢 2 を捨てた理由。** `author_name` をセッション固有にすると UI 上の名前が `Claude@unmerged-wip-check-30418a` のような文字列になり、人が読む欄を機械の都合で汚す。列を分ければ両方が正しい形を保つ
- **選択肢 4 が不可能な理由。** 「期限内なら unique」は `now()` が immutable でないので index で表現できない

## 覆す条件

- 保持者に耐久性が要るようになったとき（担当の履歴を跨いで追う、Worker と結びつける）。そのとき `claimed_by` は FK になり、これは別の設計になる
- 人間もリースを持つべきだとなったとき。今は `holder` null = 人のコメント = 延長しない。人が Element を「取る」概念が要るなら、UI から claim_element を呼ぶ経路と holder の生成規則が要る
- `stall-check` の `in_progress` 側もリースを読むように統一したとき（今は任意のコメントをハートビートとする旧経路と、刻印付きだけを数える新経路が並存している）。統一したら ADR 0007 の「解除を見張る仕組み」は完全にリースの副産物になる
