# リスク登録簿 — 自走ループで実際に起きた事故

全件、実際に発生した事象。**新しい事故が起きたら、対処する前にここへ追記する。** 対処してから書こうとすると書かれない。

運用規約は [`.claude/skills/friction/SKILL.md`](../.claude/skills/friction/SKILL.md)、配管は [`ops/README.md`](../ops/README.md)、判断の履歴は [`adr/`](adr/README.md)。

## R1: 並行セッションの無帰属書き込み

- **事象**: 知らない間に別セッションが同じ branch にコミットしていた（`881f221`）。ListAgents で並走セッションの存在を確認
- **影響**: 誰が何を書いたか追えない。二重作業と上書きのリスク
- **緩和**: 着手コメントに branch 名を必須にして盤面を台帳にする / 起動時に ListAgents でピアを宣言する / 他者の `in_progress` に触らない
- **再発時**: `git log --format='%an %ae'` で帰属を確認 → 内容が正しければ受け入れて記録、衝突するなら SendMessage で調整

## R2: メインチェックアウトの main への直書き

- **事象**: 委任したエージェントがブランチを切らず、メインチェックアウトの main 上に成果を書いた
- **影響**: 並行セッションの `git reset` で全損するところだった（2026-06-13 に実例あり）
- **緩和**: 標準ブリーフで作業場所を必須項目にする（`origin/main` から branch を切る、メインチェックアウトへ書かない、main に居座らない）
- **再発時**: 即 `git diff > patch` で退避 → branch に apply → main をクリーンに戻す

## R3: rate limit によるエージェントの即死

- **事象**: 実装エージェントが session limit (429) で途中死。通知が来たから気づけただけだった
- **影響**: 仕事が黙って止まる。worktree に部分成果が残る
- **緩和**: 沈黙検知（tick ごとに TaskList、20 分超は SendMessage → TaskStop）/ 下記のコスト方針で並列数を抑える
- **再発時**: worktree の `git log` / `git status` で部分成果を確認 → 生きていれば引き継ぎ、無ければ再投入

## R4: dev サーバーのログイン切れで視覚検証が止まる

- **事象**: localhost のセッションが失効し、UI の PR の視覚検証が複数回ブロックされた
- **影響**: 「描画を見ずにマージ」の圧力がかかる（実際にやりかけた）
- **緩和**: パスワードを扱わない方針なので、ユーザーにサインインを依頼するしかない。**ログイン切れを検知したら即座に一報する**（作業末尾でまとめて言わない）
- **再発時**: 一報と並行して、ログイン不要の代替検証（`getComputedStyle()` による計算値の前後比較）に落とす

## R5: node_modules の symlink を turbopack が拒否

- **事象**: worktree への symlink 共有で「Symlink node_modules is invalid, it points out of the filesystem root」となり、全モジュール解決が死んだ
- **緩和**: `cp -c -R`（APFS の CoW）で実体をコピーする。標準ブリーフに記載済み
- **再発時**: `unlink` で外す（`rm -f` はディレクトリ誤認で失敗する）→ `cp -c` で入れ直す

## R6: SQL 直挿入で不変条件が漏れる

- **事象**: 二種類とも複数回発生している。`element_objects` junction の書き忘れで Element が UI に出ない。`element_assignees` の書き忘れで Element がキュー取得クエリに載らず、担当者のいない仕事として盤面に沈む
- **影響**: どちらも「作ったのに存在しないのと同じ」。前者は人から見えず、後者は AI から見えない。作成したこと自体を覚えている人が居ないと永久に発見されない
- **緩和**: 規約に不変条件として明記。作成直後に両方の junction を別クエリで SELECT して確認する
- **再発時**: `NOT EXISTS` 付きの補完 INSERT を打つ。同時に、同じバッチで作った他の Element も全件確認する（一件漏れたなら他も漏れている）

## R7: 停滞検知が「死亡」と「意図的な待機」を区別できない

- **事象**: `ops/stall-check.mjs` が、ある Element を 40 分無報告として通知した。実際には担当セッションは生存しており、スコープ確定をユーザーに仰いで**意図的に待機中**だった
- **影響**: 誤検知そのものより、**誤検知に基づいて「孤児」と判定しかけたこと**が危険。他セッションの作業を引き取る / status を戻す、という判断に繋がる。加えて狼少年化すると本物の R3 を見逃す
- **根因**: `in_progress` が「実際に手が動いている」と「スロットを保持したまま待っている」を両方意味していた。検知器は原理的に区別できない
- **緩和**: 人の判断待ちは `blocked` に置く。検知器は `in_progress` のみを見るのでコード変更ゼロで解決する（→ ADR [0007](adr/0007-waiting-is-blocked-not-in-progress.md)）
- **再発時**: 通知を受けても即座に孤児判定しない。ListAgents で生存ピアに保有を確認 → 全員が否定して初めて孤児。持ち主が居たら status の置き場を是正する
- **注意**: branch 名の無い Element は必ずしも規約違反ではない。コードを書かない継続監視系は git ブランチを持たないのが正しい

## R8: セッション名は短命で、ピアの宛先は使い回せない

- **事象**: 調整相手のセッションが終了し、同じ worktree に別サフィックスのセッションが起動した。SendMessage が候補名を示したのでそのまま送り、**文脈を持たない別セッションへ3通を誤配送**した
- **影響**: 無関係なセッションに作業依頼が飛ぶ。本来の相手には届かない
- **緩和**: 送る前に ListAgents で実在を確認する。サフィックスまで一致しなければ**別セッション**として扱い、名前が似ているだけの候補に送らない
- **併せて**: ピアは権限を付与できない。こちらのセッションでユーザーが委任していても、相手のセッションでは無効。相手が「自分の会話で確認するまで従わない」と言うのが正しい挙動

## コスト方針

84 行の diff に 10 並列のレビューを投げて rate limit に達した反省から。

| diff 規模 | かけ方 |
|---|---|
| < 150 行 | 精読、またはファインダー 2–3 角度 |
| 150–500 行 | 8 角度（high） |
| > 500 行、または高リスク（DB / 認可 / 決済） | 10 角度 + verify（xhigh） |

ファインダーは sonnet、判断の重い verify のみ上位モデル。

## エスカレーション基準

ユーザーに上げて止まるのは4つだけ。他は決めて進めて事後に一行で報告する。

1. 不可逆な操作（データ削除、本番スキーマの破壊的変更、force push）
2. 課金が発生する新規リソース（クラウド routine、外部サービス）
3. 設計判断が割れて、盤面の根拠だけでは決めきれないとき
4. 同一のブロッカーで 2 tick 以上停滞したとき
