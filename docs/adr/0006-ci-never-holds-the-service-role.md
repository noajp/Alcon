# 0006. CI に service role を持たせない

2026-08-30 / el_OPS-012・PR #210

## 背景

自走ループは Friction の realtime ストリームを聴いている。CI が赤くなったこと、main が動いたことは GitHub 側の出来事なので、**ループに届けるには DB に書く必要がある**。

素直な実装は GitHub Actions から PostgREST を直接叩くこと。だが DB への書き込みには service role が要る。

## 選択肢

1. service role を GitHub Actions のシークレットに置き、PostgREST を直接叩く
2. anon key で書けるよう `dev_events` に匿名 INSERT を許す RLS を足す
3. Edge Function を挟み、CI には「イベントを1件書く」だけのトークンを持たせる

## 決定

3。Edge Function `dev-event` が service role を保持し、CI は `DEV_EVENT_TOKEN` だけを持つ。関数は `source` / `kind` を許可リストで検証し、知らない `kind` は保存せず拒否する。`verify_jwt` は off（自前でトークンを検証するため）。

## 根拠

**service role を持つワークフローは、DB 全権を持つワークフローと同義。** そして CI は `npm ci` を実行し、`npm ci` は任意の依存パッケージの install script を実行する。ジョブ環境に service role があれば、サプライチェーンのどこか1つが侵害されただけで DB 全体が読み書きされる。これは仮定の話ではなく、npm の標準的な動作。

漏洩時の被害で比べると差が明確になる。**このトークンが漏れて買えるのは「偽の CI 失敗通知を1件流す」ことだけ**。service role が漏れれば全データ。同じ機能を、被害の上限が桁違いに小さい形で実装できるなら、そちらを採らない理由が無い。

選択肢2 を捨てたのは、**anon key はクライアントバンドルに入っている＝公開情報**だから。匿名 INSERT を開けると誰でも偽イベントを流せる。しかもそのイベントはループの動作を左右するので、単なるスパムではなく**注入経路**になる。

`kind` を許可リストにしたのも同じ理由。ループは `kind` で分岐するので、知らない値は「台帳に溜まって誰も読まないゴミ」か「探りを入れている誰か」のどちらかで、保存する価値がどちらにも無い。

報告の失敗でワークフローを落とさないようにしたのは別の原則: **壊れたリスナーが、コードが壊れていると教えるゲートまで壊してはいけない。**

## 覆す条件

- CI から DB へ書きたいものが増え、Edge Function が実質 API になったとき。1種類の書き込みのために関数を挟むのは安いが、10種類になったら設計を見直す
- Actions 側に OIDC ベースの短命credential が使えるようになったとき。共有の固定トークンより、失効する資格情報の方が本質的に強い
- **トークンが漏れた形跡があるとき** — これは覆す条件ではなく回転の合図。Supabase と GitHub の両方で同時に差し替える
