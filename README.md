# Clayware

ビジネスの活動に要る仕事を、人と AI が一つの場所で行う運用基盤。対象は問い合わせ対応、営業、採用、開発、改善活動などの日々の仕事。

- **人**は目的・成功条件・権限を決め、判断と評価をする
- **AI** はその範囲で仕事を進める。権限を超えるときと、前提が崩れたときは、人に判断を求める

Clayware の中心は AIP（AI に業務をさせる仕組み）の統制 — ハーネス・アクション・承認・記録・確認。モデルと実行役は差し替えられる部品で、どのモデル・どのエージェントが動いても、同じ統制の下で動く。

## 全体像

```
┌─ 操作画面 ─────────────────────────────────────────────┐
│  Strategy（目的と成功条件）  流れのボード  判断待ち  評価  │
└──────────────────────────────▲──────────────────────────┘
                               │
┌─ AIP ───────────────────────────────────────────────────┐
│  トリガー → ハーネス → アクション → 承認 → 実行の記録 → 確認 │
│  モデル・実行役（run-agent / 外部エージェント）は差し替え可能 │
│  コネクタ（外部のサービス）                                │
└──────────────────────────────▲──────────────────────────┘
                               │
┌─ データ（Supabase）─────────────────────────────────────┐
│  名詞・リンク・アクション・記録。閲覧範囲は RLS             │
└──────────────────────────────────────────────────────────┘
```

## 概念

仕事を三つの分類で扱う。

| 分類 | 扱うもの | 単位 |
|---|---|---|
| **Strategy** | 何を達成し、どう勝つか | Strategy（入れ子にできる） |
| **Execution** | 実際の行動 | Domain → Object → Element |
| **Sustainment** | 活動を続けるための道具 | Automation / Artifacts / Reviews / Audit / People / Table / Calendar |

- **Strategy**: 目的・前提・判断・成功条件を持つ。担当と進捗は持たない
- **Domain**: 活動の場（部署・事業・案件の領域）
- **Object**: Element をまとめる持ち場。プロジェクトに近い
- **Element**: 行動の最小単位。担当・期限・進捗・依存・動詞を持つ
- **Worker**: 人（`human`）か AI（`ai_agent`）
- **Table の行**: 外の世界のもの（顧客・候補・問い合わせ）

### 動詞とアクション

- **動詞**は行動の種類。13 個で固定。
  - 人だけが行う 4 つ: 判断 `judge` / 決定 `decide` / 承認 `approve` / 回答 `answer`
  - AI も行う 9 つ: 計画 `plan` / 調査 `research` / 作成 `create` / 実行 `execute` / 検証 `verify` / 報告 `report` / 送信 `send` / 委任 `delegate` / 監視 `monitor`
- **アクション**は実行できる具体的な操作。コネクタとハーネスを足すほど増える。Clayware の操作・コネクタの操作・人の操作の三種類がある

## 仕事の流れ

仕事は二つの方向から始まり、同じ実行と確認を通る。

| 入口 | 始まり方 |
|---|---|
| 上から | 人が Strategy に目的と成功条件を書く。Planner がハーネスの分け方で Object と Element に分け、人が確かめて作る |
| 下から | トリガーが外の出来事（メール・フォーム・障害・申請）や時刻で起動する。ハーネスが分類し、Table に記録し、担当を決めて Element にする |

その後は共通。

1. AI か人が Element を実行する
2. 権限を超える操作は承認待ちになり、人が判断する
3. 成果物は検証を通ってから完了になる
4. 結果を Strategy の成功条件と照らし合わせる

## AIP の仕組み

| 要素 | 役割 |
|---|---|
| モデル | 文章を読んで判断する部品。役割（分解・実行・検証・要約）ごとに選ぶ |
| 実行役 | ハーネスに沿って仕事を進める主体。Clayware 内の `run-agent` と、外部のエージェント（Claude Code など） |
| ハーネス | 一つの仕事のやり方の定義（目録・入出力・手順・ポリシー・確認と失敗） |
| アクション | 実行できる操作の一覧 |
| コネクタ | 外部のサービスとのつながり（MCP / HTTP） |
| 承認 | 人が実行を許す仕組み。実行する入力そのもの（ハッシュ）に束縛する |
| トリガー | ハーネスを起動するきっかけ（schedule / webhook / 状態の変化） |
| 実行の記録 | 実行の一歩ずつの記録 |

統制の原則:

- AI Worker を権限の主体にし、人が委任した範囲で動かす
- エージェントは自分で承認できない。取り消せないアクションほど承認を重くする
- 資格情報は Vault に置き、モデルの文脈には出さない
- 外部から読んだ内容は指示として扱わない
- 成果物は、型の検査と別の文脈の検証役を通してから完了にする

| 状態 | 項目 |

| あり | Strategy の 1 ページと成功条件 / ハーネスの読み取りと検査 / 承認の束縛 / 検証役 / コネクタ（MCP・HTTP、Google Drive・GitHub の OAuth、Vault） / 自動化（schedule・webhook） / 流れのボード / 担当の決め方 / 業務のハーネス / Planner の出力検査 |

## 構成

- `web/` — アプリ本体（Next.js 16 + Supabase + Tailwind CSS）
- `supabase/` — migrations と Edge Functions
- `sdk/` — ローカルのアプリを Space に登録する SDK
- `docs/` — 外部向けの API・MCP・asset-relay の説明
- `website/` — LP
- `.claude/` — 開発にだけ使うもの（規則・設計・スキル・補助スクリプト）

## コマンド

```bash
cd web && npm run dev        # 開発サーバー (port 3000)
cd web && npm run build      # 本番ビルド（型検査込み）
cd web && npx tsc --noEmit   # 型チェック
cd web && npm test           # Vitest
cd web && npm run lint       # ESLint
npm run rename-product <新しい名前>   # 製品名を一括で変える
```
