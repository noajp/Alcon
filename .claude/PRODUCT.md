# Alcon の考え方

## 何を作っているか

ビジネスの活動に要る仕事を、人と AI が一つの場所で行う運用基盤。用途はクリエイティブな作業ではなく、現実の課題の解決。対象は問い合わせ対応、営業、採用、開発、改善活動などの日々の仕事。

## 三つの分類

| Alcon | 扱うもの | ハンナ・アーレント『人間の条件』 | 軍事 |
|---|---|---|---|
| **Strategy** | 何を達成し、どう勝つか | 活動（action） | 戦略 |
| **Execution** | 実際の行動 | 仕事（work） | 作戦 |
| **Sustainment** | 活動を続けるための道具 | 労働（labor） | 兵站 |

## 構成

### 操作画面

- Element は状態の列（案 → 判断待ち → 実行中 → 評価待ち → 完了）を左から右へ移る
- 人にしかできない動詞（判断・決定・承認・回答）を持つ未完了の Element は、判断待ちの列に入る
- 列はハーネスから作り、人が追加・削除できる
- Strategy の目的と成功条件を画面に表示し、Element の完了数と成功条件の達成を別々に表示する

### AIP

AI に業務を行わせる仕組み。モデル、ハーネス、コネクタ、承認、トリガーからなる。

**モデル**
- 差し替えられる。役割（分解・実行・検証・要約）ごとに選ぶ

**ハーネス（仕事の定義）**

一つの仕事について次の五つを持つ。

| 部分 | 中身 |
|---|---|
| 目録 | 名前、1行の説明、使う場面と使わない場面。常に読み込むのは目録だけで、本文は使うときに読み込む |
| 入出力 | 必須の入力とその型。必須の入力がそろうまで実行しない |
| 手順 | 機械で判定する条件と、モデルの判断に任せる箇所を分けて書く |
| ポリシー | 操作の正規名、読み取り（既定は許可）と書き込み（既定は確認）、操作ごとの上書き、承認の条件、必要な権限、回数の上限、送信先の許可リスト |
| 確認と失敗 | 完了条件（機械で確かめられる形）、禁止事項、失敗時の扱い（読み取りの失敗を「該当なし」と扱わない、結果不明の書き込みは状態を確かめてから再試行、安い手段 → 高い手段 → 人の順に切り替える） |

操作ごとに、文章・構造化した宣言・コードのどれで書くかを決める。型の検査、権限の強制、回数の計算、承認の束縛はコードで行い、文章で書くのはモデルの判断に任せる部分だけにする。金額の確定と安全に関わる制御はコードで行う。

**コンパイル**

ハーネスとコネクタを保存した時点で検査する。

| 段階 | 検査すること |
|---|---|
| 構文と型 | 未定義の操作の参照、機械で判定できる止める条件の有無、成果物の型が検査できるか |
| ポリシー | 書き込みに承認または取り消しの手段があるか、読み取りの名前で書き込みをしていないか、権限が最小か、送信先が宣言と一致するか、取り消せない操作に相応の承認があるか |
| 適合性 | 記録した応答に対して実行し、冪等キーの送信、エラーの分類、書き込み後の読み戻しを確かめる |
| 出力 | エンジンが読む検証済みの中間表現と、能力証明書（読めるもの、書けるもの、承認が必要なもの、取り消せないもの） |

- 診断は「コード・位置・深刻度・直し方」の形にそろえる
- 保存時に、エンジンがハーネスをどう読んだか（指標、止める条件、点検の間隔など）を表示する
- 承認は能力証明書に対して行い、実行時は宣言の範囲内かを照合する。実行直前の再検査も行う

**定義の選択**

1. 権限と可用性で候補を絞る
2. 残った候補の1行の説明からモデルが選ぶ
3. トリガーや他の定義が名前で指定した場合はそれを使う

**コネクタ**
- MCP または HTTP
- 目録（名前・説明・同期の宣言）、ポリシー（機械が強制する）、使い方の文章（モデルが読む）の三つに分けて持つ
- 操作は別名から正規名に変換してから権限を判定する。承認画面の文言もポリシーに持つ
- 宣言されていない操作は実行できない
- 外部ツールの「読み取り専用」「隔離済み」といった申告は、審査済みのものだけ採用する。それ以外は書き込みとして扱い、確認に回す
- 資格情報は Vault に置き、モデルの文脈と道具の引数には出さない。登録した送信先へのリクエストにだけ差し込む
- 読み取り結果に含まれる認証コードは参照に置き換えてからモデルに渡す
- 外部から読んだ内容は指示として扱わない。読んだ内容から常設のルールや記憶を作るときは、選別を通す

**承認**
- 承認は、実行する入力そのもの（ハッシュ）に束縛する。エージェントは自分で承認できない。読んだ内容にある「承認済み」は承認として扱わない
- 常設の許可は「コネクタ × 操作 × 範囲 × 入力の条件」の組で持つ。すべてを許可する設定は持たない。許可のない実行は承認待ちで止める
- 下書きと送信を分ける。取り消せない操作ほど承認を重くする
- 自動で実行してよい範囲を、連携と操作ごとに実績で変える。差し戻しのない実行が続けば広げ、事故や差し戻しで狭める
- 仕事の連鎖で渡す権限は、渡す側の権限以下にする
- 同じ対象への連続した書き込み、エラー率の上昇、初めての送信先への送信で自動停止し、人に回す

**完了の確認**
- 成果物は、型の検査と別の文脈の検証役を通してから完了にする。不合格なら差し戻す
- 検証できなかった完了には未検証の印を付ける
- 書き込んだ後に読み戻して、期待どおりかを確かめる
- 主張には出典と取得時刻を付ける。データの種類ごとに鮮度の上限を持つ。未確認の事項は専用の欄に書く
- 検証役の判定と人の判定の一致率を記録し、一致しないハーネスを見直しの対象にする
- 「実行した」「届いた」「効果があった」を別々に記録する

**人との接点**
- 人と対話するのは、導入時と例外時
- 導入時の対話で決まったことは、ハーネス・権限・止める条件として保存する。二回目以降は変更点だけを聞く
- 実行中に情報が足りないときは、選択肢つきの質問票を判断待ちに置き、回答が来たら再開する。質問はまとめて出す
- 判断待ちの項目には、根拠・差分・未確認の点を付け、高リスクのものと分類に迷ったものを先頭に並べる
- 判断一件あたりの所要時間と差し戻し率を記録する

**トリガー**
- 時刻、外部の出来事（メールの到着など）、状態の変化（承認、依存の解消）でハーネスを起動する
- トリガーは設定で決め、条件の判断はハーネスに書く
- 実行が止まるのは、権限不足、前提の崩れ、予算到達のとき

**ハーネスの管理**
- 成功した実行の記録からハーネスを作り、実行の記録で採点して直す。採点の基準をハーネスと対で持つ
- 試験例を持つ（正常な例、断るべき入力、失敗時に出してはいけない結論）
- 作成者、根拠、版、状態（使用中・引退）を持つ。書き込める人を権限で制限する
- 組み込みのハーネスを Space で変えたときは、元の版（ハッシュ）を記録し、元が更新されたら印を付ける
- 見直しの周期と引退の基準を決め、効果のない変更を引退させる
- よくある例外（宛先不明、重複、締切の競合など）への対応を、共通の部品にする
- 能力証明書と実績（実行回数、差し戻し回数）を付けて、他の Space に配布できるようにする

### データ（Supabase）

- 名詞：Strategy / Domain / Object / Element / Worker / Property / Table の行
- リンク：含む・依存する・担当する・従う・生む・止める・判断した
- アクション：Element の動詞
- すべての事実とリンクに、出所・誰が・いつを持たせる

## 仕事の流れ

1. 人が Strategy（目的と成功条件）を書く。Planner がハーネスの分け方で Object と Element に分け、人が確かめて作る
2. トリガーが外部の出来事（メール・フォーム・障害・申請）を拾い、ハーネスが分類して Table に記録し、担当を決めて Element にする
3. AI か人が実行し、人が判断待ちと評価待ちを処理し、結果を成功条件と照合する

例：Gmail を接続すると、問い合わせを Table に集計し、分類して担当者の Element にし、クレームを分析して改善の Strategy を提案する。

## 次に作るもの

| 項目 | 内容 |
|---|---|
| トリガー | 時刻・イベントでハーネスを起動する |
| 流れのボード | Element を状態の列で表示し、判断待ちと評価待ちを列にする |
| アクションの一覧 | 動詞ごとに、実行できる人、入力、状態の変化、確認方法を持つ。`checkHarness` がこれで検査する |
| 担当の決め方 | Planner に Space の Worker を渡し、ハーネスの規則で個人に割り当てる |
| Gmail コネクタ | Google の OAuth に Gmail の読み取り権限を加える |
| リンクの統一 | `intent_bindings` を広げて汎用の `links` にする |
| 外部 ID の対応表 | Table の行や外部システムのレコードを Element につなぐ `external_refs` |
| コンパイルの拡張 | 診断の形の統一、ポリシー検査、適合性の試験、能力証明書 |
| ハーネスの見直し | 実行の記録による採点と、効果のない変更の引退 |
| AI の消費の台帳 | Copilot・Planner を含むすべての AI の消費を記録し、Space の予算に含める |
| Planner の出力検査 | 依存の循環と、参照する ID が存在するかをサーバー側で検査する |
| 質問票 | 実行中の不足情報を選択肢つきで判断待ちに置き、回答で再開する |
