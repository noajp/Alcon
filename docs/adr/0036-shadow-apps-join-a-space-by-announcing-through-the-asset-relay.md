# 0036 — Shadow apps join a Space by announcing through the asset relay

## 背景

AI によって、誰もが自分の業務アプリやエージェントをローカルで作る。組織の記録と流れは、正規のシステムの外で動くそれらに散り、Alcon からは見えない。既存の入口（`alcon-api` / `alcon-mcp`、ADR 0032〜0034）は「本人として盤面を読み書きする」ためのもので、アプリ側が Alcon の概念（Element・Object）で話し、本人が個人用アクセストークンを発行して貼る必要がある。アプリを Alcon に載せ替えさせる形であり、作り手に手間を求める。

必要なのは逆向きで、アプリは Alcon の概念を知らないまま、バックエンドに一行足すだけで Space に名乗り出て、認識され、以後「何をしたか」が組織の記録に残ること（PRODUCT.md「迎えに行く接続」）。

## 選択肢

- 入口：既存の `alcon-api` に資産の経路を足す／専用の Edge Function を置く
- 最初の信頼：本人が発行したトークンを貼る／認証なしで名乗り、オーナーの承諾で成立させる／Space の共有鍵を配る
- 資産の置き場：`integrations`（オーナーがつないだ外部サービス）の一種にする／`workers`（AI Worker）の一種にする／専用の `assets` に置く
- 承諾前の出来事：受け付けない／受け付けて「未確認」と示す
- 書き込みの経路：関数が service role で表に直接書く／service role だけが呼べる RPC を通す

## 決定

- **専用の Edge Function `asset-relay` を置く。** `POST /hello`（認証なしの名乗り）・`POST /events`（資産トークンで出来事を記録）・`GET /status`。`alcon-api` は本人の JWT で RLS のもとに動く層で、ここは本人がいない。混ぜると「誰として動くか」の境界が崩れる。
- **最初の信頼は承諾で成立する。** 名乗りは Space の id と名前とメタデータだけで、鍵は要らない。受け口は資産トークン（`alc_ast_…`）を一度だけ返し、DB にはハッシュだけを置く。資産は `unclaimed` で生まれ、Space のオーナーが Settings › Integrations › Connected assets で承諾して `active` になる。所属が本人の承諾で成立する（ADR 0029）のと同じ型で、ここでは承諾する側が Space のオーナー。名乗りは Space のオーナーに `asset_announced` の通知で届く。
- **自己申告と観測を分ける。** アプリが言うこと（名前・ランタイム・ホスト・AI プロバイダの鍵の有無・依存）は `manifest`、受け口が見たこと（接続元・User-Agent）は `observed`。画面は両方を別の語で示し、承諾前の資産には「未確認」と付ける。
- **承諾前の出来事も受け付ける。** 記録は残し、未確認として示す。承諾を待っている間に何をしていたかが、承諾の判断材料になる。取り消した資産は次の呼び出しから 403 で断り、出来事も受け付けない。
- **資産は専用の `assets` / `asset_events` に置く。** `integrations` は「Alcon が外へ呼ぶ先」、`workers` は「Element に割り当てられ意図を受けて行動する主体」であり、どちらも資産の意味（外で動き、自分から名乗り出て、何をしたかを報告する道具）とは違う。同じ実体が後に Worker にも道具にもなりうるが、その境目は Decisions で判断する。
- **関数は service role だけが呼べる RPC を通す。** `announce_asset` / `resolve_asset_token` / `touch_asset` / `record_asset_events`。それぞれ一つのことしかしない。ブラウザは表に書けず、オーナーの `accept_asset` / `revoke_asset` も RPC。メンバーは読める（ハッシュを除く）。
- **名乗りは Space ごとに上限を持つ。** 認証なしの入口なので、未承諾の資産が 100 件を超えた Space への名乗りは 429 で断る。オーナーが承諾か取り消しで減らす。
- **SDK は一行で、何も壊さない。** `sdk/node/alcon.mjs` / `sdk/python/alcon.py` は依存なし、import で名乗り、トークンを `.alcon/asset.json` に保持し、起動・停止・外向き HTTP のホスト名・アプリが言う出来事を 5 秒ごとにまとめて送る。受け口に届かない・取り消された・設定が無い、のどれでもアプリは止まらない。要求の本文・環境変数の値・ファイルの中身は送らない。

## 根拠

トークンを貼らせる形は、既存の `alcon-api` で今日でもできる。それでもシャドウアプリが来ないのは、作り手に「Alcon の側の作業」を求めるからで、Sentry や Datadog が一行で広まったのは、足すコストがゼロに近く、足した瞬間に向こうが見えるから。名乗りを認証なしにし、承諾をオーナー側に置くことで、作り手の作業は一行と環境変数 2 つになる。

認証なしの入口は、なりすましと流量の問題を持つ。だから名乗りは「未確認」で始まり、Space のオーナーが見て承諾するまで資産にならず、承諾前も後も自己申告は観測と別に示す。Space の id を知るだけで名乗れるのは意図的で、その代わり未承諾の数に上限を置く。

`integrations` に混ぜると、オーナーが「外へ呼ぶ先」として貼った資格情報と、外から来た自己申告が同じ一覧に並び、信頼の向きが読めなくなる。`workers` に混ぜると、資産が Element の担当として割り当てられ、`worker_assignable` の判定に入ってしまう。

## 覆す条件

- 一行を足したアプリが実際には来ない（初期顧客の運用で、正規のシステムの外に散った記録の負担が確認できない）なら、受け口は維持費だけになる
- 承諾前の出来事を受け付けることで、未承諾の資産からの流量が Space の表示や DB を圧迫するなら、承諾前は名乗りだけにする
- 資産が Element の担当として行動する用途が主になるなら、`workers` との統合を Decisions で再判断する
- Space の id だけで名乗れることが実際の悪用を招くなら、Space ごとの受付コードを足す
