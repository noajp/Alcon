# 0047 — 承認は内容のハッシュに結び、証明を発行する時に1回だけ消費する

## 背景

ゲートウェイ（ADR 0045・0046）は、返信の送信や支払いのように人の判断が要る操作の前に、人の承認を求める。承認が「その内容を送ってよい」という意味を持つには、承認した後に内容をすり替えられないこと、同じ承認を2回使えないこと、承認したのが本当にその Space の判断者であることを、ゲートウェイと監査の双方が確かめられなければならない。Alcon は書類の中身を持たない（ADR 0044）ので、承認する人は中身ではなく、ゲートウェイが書いた要約を読んで判断する。

Alcon 内のエージェントの承認（`agent_actions`、ADR 0027）は、Alcon の実行（`agent_runs`）と Element に結びつき、Alcon 自身が操作を実行する。ゲートウェイの操作は Alcon の外で行われ、Element を持たない。

## 選択肢

1. `agent_actions` を広げ、ゲートウェイの依頼も同じ表に入れる
2. ゲートウェイの承認を別の表に置き、承認されたら署名つきの証明を発行し、ゲートウェイが後で消費を報告する
3. ゲートウェイの承認を別の表に置き、ゲートウェイが送る直前に、送る内容のハッシュを添えて「引き換え」る。DB が承認を1回だけ消費し、その時に証明を発行する

## 決定

3 を採る。

- 依頼は `workflow_approvals` に置く。導入・実行・接続・操作・内容の SHA-256（`input_hash`、内容そのものは持たない）・判断する人が読む要約・期限（5分〜24時間、既定24時間）を持つ。依頼は Edge Function `audit-approvals` が、記録の受け口と同じゲートウェイの鍵の署名で受ける。`request_id` で冪等にし、同じ id で内容が違えば拒否する。鍵の Space の外の導入は拒否する
- 依頼が届くと、Space のオーナー全員の Inbox に通知が届く（`notifications.workflow_approval_id`）。判断できるのは Space のオーナーが本人としてログインしているときだけで、委任された呼び出し（個人アクセストークン・OAuth）からは判断できない。期限を過ぎた依頼は判断できない。Audit のワークフローの概況にも、判断を待つ依頼を出す（通知の種類をミュートしても判断できるように）
- ゲートウェイは送る直前に、送る内容のハッシュを添えて引き換える。DB は行をロックし、承認済み・期限内・未使用・ハッシュ一致のときだけ消費の時刻を記録し、`audit-approvals` が Alcon の鍵（`AUDIT_GRANTS_SIGNING_KEY`、権限表と同じ鍵。本文の `kind` で区別する）で証明に署名して返す。証明は消費の時に1回だけ発行され、発行から10分で期限が切れる。ハッシュが違えば消費せずに `mismatch` を返し、2回目は `used` を返す
- ゲートウェイは証明を、導入時に固定した Alcon の公開鍵で確かめ、承認の id・送る内容のハッシュ・期限を照合してから送る（参照実装は `_shared/auditApprovals.ts` の `readApprovalProof`）
- 承認の行は削除できず（Space の削除による cascade だけは通す）、関数以外からは書き換えられない

## 根拠

- 1 は、`agent_actions` の Element・実行・RLS（Element の可視性）がゲートウェイの依頼に合わない。Alcon が実行するものと外で実行されるものの約束が混ざる
- 2 は、証明を発行してから消費の報告までの間に、同じ証明が2回使われうる。報告が届かなければ、Alcon は使われたかどうかを知らない。3 は消費と発行が同じトランザクションなので、証明が存在すること自体が「1回目の使用」を意味する
- ハッシュを引き換えの時に DB が照合するので、承認の後に内容が変わった送信には証明が出ない。証明にもハッシュが入るので、ゲートウェイの側でも照合できる

## 覆す条件

- 引き換えの応答がゲートウェイに届かず、承認を取り直す手間が業務上許されない場合 → 同じ鍵・同じハッシュでの再引き換えに限り、同じ証明を再発行する（消費の時刻は変えない）
- オーナー以外にも判断を任せる必要が出た場合（部門の責任者、金額のしきい値など）→ 承認者と条件をワークフローの設定（ELE_AUD-007）に持たせ、`decide_workflow_approval` がそれを読む
- 要約だけでは判断できない業務が出た場合 → 内容は顧客のストレージに置いたまま、承認画面からそこを開く導線を足す（Alcon に中身は置かない）
- 権限表と承認の証明で署名鍵を分ける必要が出た場合（片方だけ替えたい、運用者を分けたい）→ 証明用の秘密を足し、`kind` ごとに別の公開鍵を固定させる
