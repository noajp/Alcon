# 0007. 人の判断待ちは blocked であって in_progress ではない

2026-08-30 / el_OPS-013 の停滞誤検知から

## 背景

停滞検知（`ops/stall-check.mjs`）を稼働させた直後、`el_OPS-013`（Sprint 計測）を「40分間 in_progress のまま進捗報告なし」として通知した。

**誤検知だった。** 担当セッションは生きており、Sprint 2 のスコープ確定をユーザーに仰いで意図的に待機していた。

危険だったのは通知そのものより、**それを根拠に「担当セッションが死んだ孤児」と判定しかけたこと**。他セッションの作業を引き取るか status を戻すか、という判断の一歩手前まで行った。

## 選択肢

1. 停滞検知に除外条件を足す（継続監視系 Element、branch を持たないもの等）
2. `waiting_for_user` のような status を新設する
3. 人の判断待ちを既存の `blocked` に置く

## 決定

3。継続監視系の Element が自分のサイクルを終えてユーザー判断待ちになったら、`in_progress` に留めず `blocked` + `■ Blocked` コメントに落とす。判断が来たら `in_progress` に戻す。

## 根拠

根本原因は**検知器ではなく状態の意味**にある。`in_progress` が「今まさに手が動いている」と「スロットを保持したまま待っている」の両方を指していたので、**盤面からその区別が原理的にできない**。検知器側でどう工夫しても、区別できない情報から区別を作ることはできない。

`blocked` に置けば解決するのは、停滞検知が `status = in_progress` だけを対象にしているから。**コード変更がゼロで済む。** 除外条件を足す（選択肢1）と、その条件自体が次のメンテ対象になり、条件に当てはまらない新種が出るたびに増える。

新 status（選択肢2）を作らなかったのは、`blocked` が既にその意味を持っているから。プロトコルの `■ Blocked — 原因と必要な判断` という書式は、まさに「必要な判断を待っている」ことを書くためにある。**新しい状態ではなく、既にある状態の使い方の問題だった。**

そして副次的だが効くのが、**盤面が正直になること**。何も進んでいないものを in_progress と表示するのは嘘で、burn-up の数字にも効く。誤検知を招いたのも、盤面が「作業中」と表示していたから。

## 覆す条件

- 「待ち」の種類を区別したくなったとき（人待ち / 他 Element 待ち / 外部要因待ち）。`blocked` が混み合って理由をコメントから読まないと分からなくなったら、その時が status を割る時
- ブロック解除の検知を自動化したくなったとき。今は人が戻す。依存関係（el_TRJ-003）が入れば「ブロッカーが done になったら候補に戻す」が書けるが、それには何にブロックされているかが構造化されている必要がある
- **前提が消えたのに blocked のままの Element が再び出たとき。** `el_UXQ-009` がまさにそれで、保留理由（InlineAddRow の存在）が消えたのに誰も気づかず沈んだ。blocked に落とす運用は、解除を見張る仕組みとセットでなければ別の沈み方をする
