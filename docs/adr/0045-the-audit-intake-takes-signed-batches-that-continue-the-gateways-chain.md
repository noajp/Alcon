# 0045 — 記録の受け口は、署名されたまとめ送りを受け、ゲートウェイの鎖が続いているかを確かめる

## 背景

AI の監査台帳（ADR 0044）は、外部の実行基盤（Metaxy のゲートウェイ）が関節で残した記録を受け取る。台帳への書き込みは service role が要るが、service role をゲートウェイに渡すと、漏れたときに全テナントのデータを持っていかれる。ゲートウェイは送信待ちの箱からまとめて送り、通信が切れれば同じまとめを送り直す。途中の記録が抜けたり、順番が入れ替わったりしたまま台帳に入ると、DB の鎖（ADR 0044）は「入った記録が書き換わっていない」ことしか示せず、「届くべき記録が全部届いた」ことは示せない。

## 選択肢

1. ゲートウェイごとに共有シークレット（`dev-event` と同じトークン）を持たせる
2. ゲートウェイごとに Ed25519 の鍵ペアを持たせ、Alcon には公開鍵だけを登録する。本文全体に署名して送る
3. mTLS でゲートウェイを認証する

抜けの検出について：

- a. ゲートウェイが連番を振り、受け口が欠番を見る
- b. ゲートウェイが記録ごとに、前の記録のダイジェストを含むダイジェストを付け（ゲートウェイ側の鎖）、受け口がその続きかを見る

## 決定

2 と b を採る。

- 鍵は Space に登録する（`workflow_gateway_keys`）。登録と失効は Space のオーナーだけが行う。鍵は書き換えも削除もできず、変えられるのは失効だけで、失効は戻せない。鍵を替えるときは新しい行を作る
- 受け口は Edge Function `audit-intake`（JWT 検証なし。署名が認証）。鍵の id と、生の本文に対する署名をヘッダーで受ける。未登録・失効済み・署名違いは同じ 401 を返し、どの鍵 id が存在するかを漏らさない
- 1つの鍵が書けるのは、その鍵の Space にある導入だけ
- 各記録（手順）は `event_id` と、`prev_digest`・`digest` を持つ。`digest` はフィールドをバイト長つきで連結した文字列の SHA-256 で、`prev_digest` を含む（`_shared/auditIntake.ts` の `eventDigestText` が正本）。時刻は UTC・マイクロ秒・`Z` の1通りの書き方だけを受け付け、書き方の違いでダイジェストが変わらないようにする
- 文字列は jsonb に入るものだけ（NUL と対のないサロゲートは拒否）、時刻は実在するものだけを受け付ける。DB に入らない入力を送り直しの効く失敗にすると、ゲートウェイの送信待ちの箱が同じまとめで止まり続けるため、署名の通ったまとめの不正は拒否（409）として残す。DB の混雑（デッドロックなど）による失敗だけを 503 にして、同じまとめを送り直させる
- 受け口は、各記録のダイジェストがフィールドから再計算した値と一致すること、まとめの中で導入ごとに前の記録を指していることを確かめる。DB の `workflow_intake` は、まとめが指す導入の行を id 順にすべてロックしたうえで、導入ごとの最初の新しい記録が、保存済みの最後の記録の `digest` を指していることを確かめる。切れていればまとめ全体を拒否し、409 と理由を返す
- 冪等性は2段で持つ。同じ鍵・同じ `batch_id`・同じ本文は `duplicate` を返して何も書かない。同じ `batch_id` で本文が違えば拒否する。別の `batch_id` で送り直された記録は、保存済みの記録と `digest` が一致し、新しい記録より前にある限り読み飛ばす。実行は `(deployment_id, external_id)` で1つに決まり、保存済みと内容が違えば拒否する
- まとめは全部入るか、何も入らないかのどちらか。署名の通ったまとめは、受け入れも拒否も `workflow_intake_batches` に残り、Space のオーナーが読める
- ゲートウェイ側の鎖と DB 側の鎖（ADR 0044）は別々に持つ。DB 側の鎖はゲートウェイが知らない値（実行の id）を含むので、ゲートウェイは計算できない。ゲートウェイ側の鎖は「届くべきものが届いた」を、DB 側の鎖は「入ったものが書き換わっていない」を示す

## 根拠

- 1 は、シークレットを Alcon も持つので、Alcon 側から漏れても偽造できる。2 は Alcon が公開鍵しか持たないので、Alcon のデータが漏れても記録は偽造できない
- 3 は Edge Functions の前段で終端されるため、関数の中でクライアント証明書を確かめられない
- a は欠番を検出できるが、記録の中身が送信途中で差し替わったことは署名に頼るしかない。b は記録ごとのダイジェストが鎖になるので、後でゲートウェイの手元の記録と台帳を突き合わせるだけで照合できる

## 覆す条件

- 1つの Space に複数のゲートウェイを置き、同じ導入へ並行して書く必要が出た場合 → 鎖を導入×鍵で分け、`prev_digest` の照合も鍵ごとに行う
- まとめが大きくなり、1トランザクションでの書き込みが受け口の時間制限に近づいた場合 → まとめの上限（現在 1000 件・1MB）を下げ、ゲートウェイ側で分割させる
- 鍵の管理をゲートウェイの運用者（Metaxy）に任せる必要が出た場合 → Space のオーナーではなく、運用者の Worker が登録できる経路を足す
- 拒否されたまとめを、オーナーへの通知として届ける必要が出た場合 → `notifications.kind` に種類を足し、拒否のたびにオーナーへ1行書く
