# 0005. 自走ループを時計ではなくイベントで駆動する

2026-08-30 / el_OPS-012・PR #210

## 背景

`el_OPS-012` は当初「SV（監督）を cron 化して自走を成立させる」だった。定期的に起き、盤面に変化が無いかを問い合わせ、また眠る。

しかし **盤面はすでに push している。** `elements` / `element_comments` / `element_assignees` は `supabase_realtime` publication に入っている（PR #194）。変化はリスナーに即座に届く。

放送しているものを定期的に取りに行くのは、**仕事の進む速さと無関係な遅延の下限を自分で作る**ということ。

## 選択肢

1. cron で定期的に盤面を問い合わせる
2. リアルタイム購読でイベントを受ける
3. 両方（イベント駆動＋定期の健全性確認）

## 決定

3。ただし**時計の役割を厳密に1つに限定する**。

イベント源は3つ。エージェント完了（ハーネスネイティブ、配線不要）、盤面の変化（`ops/board-listen.mjs` が realtime を購読）、リポジトリのイベント（GitHub Actions → `dev_events` → 同じストリームに合流）。

時計が残るのは `ops/stall-check.mjs` のみ。**「仕事はあるか」ではなく「working と名乗ったまま黙っていないか」だけを訊く。**

## 根拠

ループの周期が**仕事の完了速度に一致する**。エージェント完了が支配的なイベントで、これは配線が要らない。

盤面が push であることの副産物として、**カードを動かすことがそのまま指示になる**。Element を Sprint に入れる、優先度を上げる、コメントを書く — どれもポーリング間隔を待たずに届く。盤面が単一情報源であるという設計が、ここで初めて操作面としても働く。

時計を完全には捨てられない理由は1つだけ。**イベントでは「来なかったイベント」を検知できない。** rate limit で死んだエージェントは何も書かず、行は in_progress のまま健全に見える。これだけは定期的に見に行くしかない。だから時計は仕事を生まず、警報だけを生む。健全な間は無出力で、**沈黙が正常な状態**。

ハートビートに `updated_at` ではなく進捗コメントを使ったのは、`updated_at` は編集でも動くので死んだエージェントと区別できないため。

## 覆す条件

- **ラップトップを閉じても回したくなったとき。** これが最大の限界で、この構成は解決しない。リスナーも停滞検知もローカルセッションで動くので、セッションが死ねば全部止まる。無人稼働が要件になった時点でクラウド routine が要り、そこには課金が伴う
- realtime の購読が信頼できないと分かったとき（取りこぼしの実測）。その場合は「イベントで起き、起きたら差分を問い合わせる」形に変える。イベントを**通知**としてだけ使い、**データ源**としては使わない
- 並行セッションが増えて同じイベントに複数が反応し始めたとき。今は `dev_control.max_concurrent` が上限を示すだけで強制していない
