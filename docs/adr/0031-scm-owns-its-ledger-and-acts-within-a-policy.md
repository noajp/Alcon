# 0031 — SCM owns its ledger and acts within a policy

## 背景

SCM は CRM と同じ `operations-planner` で動いていた。利用者の Table の列を「品目・在庫・日次需要・リードタイム・発注残・入荷予定日」に対応付け、1 行 1 品目・1 入荷予定として補充数量を試算する。この形では、需要は人が入力した 1 つの数字で、履歴から学べない。拠点は持てず、発注は 1 行に 1 件しか書けず、入荷で在庫が増えず、仕入先の遅れも記録されない。計算の前提（需要のばらつき・実際のリードタイム・発注の状態）がデータに無いので、安全在庫・欠品日・発注案を根拠つきで出せなかった。サイドバーは画面内のタブを繰り返すだけで、どこに注意が要るかを示さなかった。

## 選択肢

- データの置き場：Table の列対応を広げる（品目・入出庫・発注を別々の Table に置き、名前で突き合わせる）／SCM 専用の表を持つ
- 在庫の持ち方：在庫数を直接書く／入出庫台帳から導く
- AI の権限：提案だけ／方針の範囲内で発注まで行い、超える分は人の承認に回す
- 計画の実行場所：ブラウザ／サーバー（Edge Function・定時実行）

## 決定

- **SCM は専用の表を持つ。** `scm_locations` / `scm_suppliers` / `scm_items` / `scm_stock` / `scm_movements` / `scm_purchase_orders` / `scm_po_lines` / `scm_policies` / `scm_autopilot_runs`。行は Space に属し、その Space のメンバーが読み書きする（RLS は `is_activity_space_member`）。表どうしの参照は `(id, activity_space_id)` の複合外部キーで、別の Space の行を指せない。
- **在庫は台帳から導く。** `scm_movements` は追記のみ（UPDATE / DELETE のポリシーが無い）。トリガが `scm_stock.on_hand` を更新する。訂正は棚卸（`scm_count_stock` が差分を adjust として書く）か adjust の行で残す。入荷は `scm_receive_po` が台帳・入荷数量・発注の状態を 1 トランザクションで動かす。
- **計画は 1 つの純粋関数（`scmEngine.planScm`）。** ブラウザと Copilot（`scmPlanner`）が同じものを使う。需要予測（減衰トレンド＋曜日係数、欠品日の補完）、サービス水準と需要・リードタイムのばらつきからの安全在庫、仕入先の実績による実リードタイム、既存発注と方針どおりの将来発注を含む日次の見通し、発注案の仕入先・拠点ごとのまとめ、拠点間移動・既存発注の前倒しの提示。
- **AI は方針の範囲で動く。** 方針（`scm_policies`）は人が示す意図：サービス水準・計画期間・発注間隔・月次予算・自動承認の上限。オートパイロットは上限内かつ予算内の発注だけを承認済みで出し、ほかは下書きにして承認者の Element を起票する。SCM で承認・却下すると Element も閉じる。Copilot は下書きしか作れない。発注には根拠を書き、オートパイロットの実行は `scm_autopilot_runs` に残す。
- **オートパイロットは SCM を開いたときに 1 日 1 回、ブラウザで走る。** 定時のサーバー実行は持たない。

## 根拠

Table の列対応を広げると、品目・入出庫・発注の関係を名前の一致で保つことになり、入荷で在庫を増やす・発注の残を数えるといった整合を、型も制約も無い セルの上で守ることになる。SCM の価値は計算の前提が正しいことにあり、その前提は表の制約と台帳でしか保てない。CRM は 1 行で完結する商談なので Table の見せ方のままにした。

在庫数を直接書けば速いが、需要の履歴・遅れの実績・訂正の跡が残らず、計画が学ぶ材料も、数字を確かめる根拠も失う。台帳から導けば「なぜこの在庫数か」に必ず答えられる。

AI に提案だけをさせると、毎回の発注が人の作業として残り「任せる」が成り立たない。上限なしに任せれば、予算と責任の所在が曖昧になる。人が上限と予算を示し、超える分は Element として人の判断に戻すのは、「意図で委ね、成果と根拠で確かめる」をそのまま形にしたもの。

定時のサーバー実行は、無人で発注を作ること自体が課金・権限を伴う判断であり（friction の停止条件）、まずは人が SCM を開く行為に結びつけた。

## 覆す条件

- **品目×拠点が数千を超え、ブラウザでの計画が数秒を超える** → 計画をサーバー（Edge Function か SQL）に移し、結果を保存する。
- **オートパイロットを人が開かなくても回したい** という判断が DEC で承認された → 定時実行（scheduled task / pg_cron）を足す。権限の判定は `placeProposals` と同じ規則を使う。
- **外部の在庫・発注システム（ERP / EC）と同期する** → 台帳の行に出所（`source`）と外部 ID を足し、取り込みを冪等にする。台帳から在庫を導く形は変えない。
- **複数通貨の予算** が要る → 予算を通貨ごとに持つ。今は方針の通貨と異なる発注を予算の判定に入れない。
