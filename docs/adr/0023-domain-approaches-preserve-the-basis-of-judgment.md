# 0023 — Domain の構想と判断根拠を保存する

## 背景

複数の Object が完了しても、Initiative の成立条件を満たしたとは限らない。Domain では、作業の組み合わせと成果の関係を仮説として記し、観測によって見直す必要がある。

## 選択肢

- Object の進捗集計だけで Domain を評価する。
- Widget の設定や自由記述だけに構想・評価を置く。
- 構想・成立条件・貢献・評価・レビューを関連する永続レコードとして保存する。

## 決定

Domain は継続する活動の場で、複数の構想を持つ。構想は一つの Initiative と任意の既存 measure を参照する。Object の階層は増やさず、条件への貢献を関連として保存する。

観測事実・出典・観測日と解釈を分離した評価、継続・変更・停止のレビューは追記する。DB が判断者と日時を刻み、レビュー時点の構想・条件・貢献・評価をスナップショット化する。構想・条件・貢献の変更で計画版を進め、以前の評価を再評価対象にする。レビューと編集には版照合を行い、並行更新による上書きを拒否する。

閲覧には Domain と Initiative の両方の可視性、構想や判断の記録には Domain owner/admin の権限を要求する。Object のリンクはその Domain に属する可視 Object に限る。RLS と invoker 関数で API 経由にも同じ境界を適用する。停止は構想に対する判断であり、Object の実行状態を自動変更しない。

## 根拠

条件と成果物を分けると、代替手段や学習による停止を扱える。判断当時の根拠を残すことで、後の編集が過去の判断を正当化するように履歴を書き換えることを防ぐ。既存の Initiative の意図と Object の行動を往復できるまま、作業一覧には存在しない判断を Domain に置ける。

## 覆す条件

計画の軽微な変更で無関係な評価の再確認が過剰に生じる場合は、条件単位の根拠適用範囲を導入する。owner/admin 以外による評価が実運用に必要な場合は、観測の投稿と構想の判断の権限を分ける。複数 Domain をまたぐ競合の比較は、可視範囲と判断責任を実例で確認して拡張する。
