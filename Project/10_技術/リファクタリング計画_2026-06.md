## 2. 進め方の原則

1. **小PRで main に即マージ。** リモートに長命ブランチを残さない(既存運用どおり)
2. 各PRの完了条件: `cd web && npx tsc --noEmit` / `npm run build` / 触ったビューのスモーク確認
3. 挙動変更を伴うリファクタと見た目の変更を同一PRに混ぜない
4. 共通コンポーネント抽出は「**抽出PR(新規追加+1箇所置換)→ 適用PR(残り全箇所置換)**」の2段階で差分を小さく
5. DB変更は必ず migration ファイルとして `supabase/migrations/` に残す

## 6. リスクと緩和

| リスク | 緩和 |
|---|---|
| RLS変更で自分の正規アクセスまで壊す | migration 適用前に SQL でポリシーを SELECT 検証。適用後に全ビューのスモーク |
| viewRegistry 切替時のビュー消失 | 並走期間を設け、1ビューずつ切替。`ViewId` 型で文字列typoをコンパイルエラー化 |
| useSupabase 分割の影響範囲 | 再export で旧パス互換を維持し、呼び出し側移行を機械的に分割 |
| 削除したつもりの「死んだ」コードが実は将来用 | PRを削除専用にして revert を容易に。git履歴に残るので復元可能なことをPR本文に明記 |
