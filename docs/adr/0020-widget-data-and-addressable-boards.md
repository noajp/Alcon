# 0020 — Widget は永続データを参照し、配置を対象別に保存する

## 背景

人間とAIが個別データ・情報・分析の構造をCRUDし、同じデータを異なる表示に配置できる必要がある。コンポーネントの定数とブラウザだけの配置では、データの編集も対象別の構成も共有のAPIから扱えない。

## 選択肢

- Widgetごとに独自のデータと編集UIを持つ。
- 配置のJSONへデータを埋め込む。
- 既存のTableを任意データと構造の保存先にし、Widgetは参照と表示設定を持つ。

## 決定

任意の項目・分類・数値はTableの列・行・セルで表現する。`data-view` は同じTableを表・カード・棒グラフとして表示し、編集UIとCopilotの `tableData` が同じ行をCRUDする。既存のCampaignフレームワークはintentsを参照する。

`widget_boards` はユーザーと `surface:subjectId` の組に配置を保存する。HomeはSpaceを対象とする。配置はTableへの参照・表示列・分類・軸・タイトルを持ち、業務データを持たない。人間の更新とCopilotの `widgetBoard` はrevisionで競合を検出する。既存ブラウザ配置はサーバー保存がないときだけ初期配置として読む。

Tableは既存の所有者RLSを維持し、配置も個人所有とする。配置を削除しても参照先Tableを削除しない。セルの行と列が同じTableに属することをDBでも強制する。Realtimeは表示中の配置とデータの再取得を駆動する。

## 根拠

構造と値を既存の保存先に置けば、表示を増やしてもデータが複製されない。JWTとRLSを通る同じAPIを使うことで人間とAIの権限が一致する。対象別配置は別CampaignやObjectへの設定の漏れを防ぎ、revisionは同時編集による上書きを防ぐ。

## 覆す条件

組織で同じTable・配置を共同編集する要求が具体化したら、TableとBoard双方にSpace/Domainメンバーシップを導入する。配置だけを共有して個人データへの参照を配布しない。表では表現できない関係構造が必要になったら、既存概念に帰属させるかを検討したうえで保存モデルを拡張する。
