# 0013 — 規約は原則の派生として書き、規約の変更は人間がマージする

## 背景

friction の規約（`.claude/skills/friction/SKILL.md`）は事故のたびに規則が1つ増える形で育った。`--delete-branch` の失敗、display_id の再採番、main 参照の占有 — どれも正しい規則だが、規則は起きたことしか覆えない。初見の状況で沈黙し、フィードバックをどの高度に焼き込めばいいかも教えない。

還流も場当たりだった。事故は risk register に、レビューの指摘は「還流した条項」節に、不満は Element に — ただしどれも、メインセッションが実装の片手間に気づいたときだけ。事故未満のシグナル（承認されなかった提案、繰り返される同種のレビュー指摘、Element 記述不足の迷い）は収穫されずに流れていた。

もう1つの制約はトークン。規約・CLAUDE.md・スキルはセッションごとに読まれるので、恒久 md の1行は一度きりのコストではなく永続コストになる。改善のたびに文書が太る設計は自壊する。

## 選択肢

1. 現状維持 — 規則の山を維持し、還流は場当たりのまま
2. 独立した改善スキルを登録し、スケジュール実行する（Warp の二スキル構成の直訳）
3. SKILL.md に原則層を足し、改善工程は friction スキル内の参照ファイル（IMPROVE.md）としてスプリント境界にだけ読む。規約を変える PR は人間がマージする

## 決定

3。原則9項を SKILL.md の冒頭に置き、既存の規則をその派生として読む。スプリント境界（キューが空）で IMPROVE.md の観察工程が5系統（PR レビュー / Blocked / 提案の否認 / dev_events / risk register）を収穫し、規約への最小差分 PR に変換する。規約（`.claude/skills/` / `docs/adr/` / `CLAUDE.md`）を変える PR は自己マージせず、ユーザー承認がループを閉じる。規約のサイズはラチェット — 行を足すなら同じ重さの削除を先に検討し、同型規則の並びは原則へ圧縮する。

## 根拠

- 原則は規則の圧縮形。初見の状況を判断でき、フィードバックの焼き込み先（規則の欠けか原則の欠けか）を与え、トークンも規則の列挙より安い
- 案2を捨てた理由は二つ。スキル登録は説明文が全セッションのコンテキストに載る（IMPROVE.md ならスプリント境界にしか読まれない）。スケジュール実行は ADR 0005（イベント駆動）に反し、キュー空という既存のイベントで足りる
- 人間ゲートは安全装置。自己修正系が自分の制約を自分で書き換えられるなら、間違ったフィードバックの混入を止める場所が無い。実装 PR と規約 PR で扱いを分けるのは、前者の誤りはコードレビューと現物検証で捕まるが、後者の誤りは以後の全セッションの前提になるため
- 案1を捨てた理由: 規則の山は既に「原則部分が弱い」という形で運用者に観測されていた。育て方を変えない限り同じ観測が繰り返される

## 覆す条件

- エージェントの役割が分化し（実装 / トリアージ / レビューが別ループを持つ）、単一の IMPROVE.md では収穫が混ざるようになったら、役割ごとの改善工程に分割する
- 規約差分 PR が承認待ちで恒常的に滞留するなら、人間ゲートがボトルネック — 軽微な派生規則の追加に限り自己マージを許す等、ゲートの粒度を再設計する
- どの原則からも導けない規則が増え続けるなら、原則の組が現実を覆えていない — 層の設計自体をやり直す
- 収穫が数スプリント連続で空振りするなら、定例をやめて「シグナルが溜まったとき」のオンデマンドに落とす
