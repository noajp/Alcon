# 0002. 活動集計をサーバー側 RPC でやる

2026-08-30 / el_TRJ-001・PR #192

## 背景

リストの各 Element に「コメントが何件あり、最後はいつか」を出したかった。素直に書くと、表示中の Element 全部のコメント行を取ってきてクライアントで数えることになる。

これは3つ壊れる。表示100件で各10コメントなら1000行が飛ぶ。element_id を URL のクエリに並べるので**表示数が増えると URL 長の上限に当たる**。そして PostgREST には行数上限があり、**上限に達しても切り捨てが黙って起きる** — 集計が静かに間違った値を出す。

## 選択肢

1. コメント行をクライアントに取って数える
2. マテリアライズドビュー / 集計列を `elements` に持ち、トリガで更新
3. サーバー側の集計関数を RPC で呼ぶ

## 決定

3。`get_element_activity(p_element_ids uuid[])` が `(element_id, comment_count, last_comment_at)` を返す。`security invoker`、`search_path` 固定。`useElementActivity` から rpc（POST）で呼ぶ。

## 根拠

応答が **O(Element 数) であって O(コメント数) ではない**ので、行数上限に構造的に当たらない。切り捨てが起きないなら、切り捨てが黙って起きる問題も消える。POST で呼ぶので id の配列は body に載り、URL 長の制約も外れる。

`security definer` ではなく **`security invoker` にしたのが要点**。element_comments の RLS が呼び出し元に適用されるので、**見えないコメントの件数が漏れることが原理的に起こらない**。集計値は「何件あるか」を通じて存在を漏らしうるので、ここを definer にすると RLS を迂回する穴になる。

選択肢2（集計列 + トリガ）を採らなかったのは、非正規化した値は必ずいつか実態とずれるから。コメントの削除・移動・一括操作のたびに整合を保つコードが要る。読み取りのたびに数える方が、この規模では安い。

## 覆す条件

- コメント数が1 Element あたり数千規模になり、毎回の集計が実測で重くなったとき。その時点で初めて選択肢2（トリガ更新の集計列）が割に合う
- 集計をリスト表示以外（横断ダッシュボード、時系列）でも使いたくなったとき。用途が増えるなら関数を増やすより実体を持つ方が整理しやすい
- **`security invoker` を外したくなったら、それは覆す条件ではなく警告**。集計が RLS を越えて見えるべき理由は、少なくとも今は無い
