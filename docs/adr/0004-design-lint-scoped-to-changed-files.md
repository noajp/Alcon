# 0004. design-lint を変更ファイル限定のラチェットにする

2026-08-30 / el_OPS-008・PR #197

## 背景

CLAUDE.md には ESLint で表現できないハウスルールがある — ラベルを全大文字にしない、入力に枠・リングを付けない、色を直書きしない、「Task」と呼ばない。**規約が散文にしか無く、何も検査していなかった。**

結果は 2026年8月のスイープが示した通り: 全大文字ラベル約40件、色の直書き約120件、リング付き入力19件。**規約が散文だったからこそ溜まった。**

## 選択肢

1. 全ツリーを検査して違反ゼロを要求する
2. 全ツリーを検査するが警告のみ（落とさない）
3. 変更ファイルだけを検査し、ベースより増えた分だけ落とす

## 決定

3。既定は `--changed`（origin/main との差分ファイル）。その中でも**ベースブランチに既に存在した違反は報告するが落とさない。純増だけが落ちる。** 全ツリーは `--all` で監査として回す。例外は `design-lint-ignore` コメントに理由を添えて明示。

## 根拠

1 は正しく見えて機能しない。**200件超の既存違反がある状態で全ツリーゲートを入れると、全ての PR が赤くなり、1週間で誰も見なくなる。** 動かないゲートはゲートではない。

2 は落ちないので、赤が増えても誰も止まらない。溜まった経緯そのものの再現。

3 が効くのは「出血を止める」ことに絞っているから。今日から入る違反はゼロにでき、既存分は専用の掃除 PR で順に返せる。

**ファイル単位ではなくラチェットにしたのは実測の結果。** ファイル単位版を最初の PR に当てたら、変更箇所の隣にあっただけの既存違反で止まった。掃除すること自体は正しいが、**無関係な PR の条件にするのは間違い**で、`ListTable.tsx` のような大きな違反ファイルに触る人は永久に前に進めなくなる。ESLint に対して手作業でやっていた「ベースと比べ、既に壊れている分は許し、悪化だけ拒む」と同じ規則を機械化した。

規則とマッチャ（`scan`）とラチェット本体を `designLintRules.mjs` に分離し、CLI は「どのファイルを見るか・ベースに何があったか・どう出すか」だけを持つ。規則が純粋関数なのでユニットテストが書ける。

## 覆す条件

- **既存違反が実質ゼロまで減ったとき。** そうなれば全ツリーゲート（選択肢1）に切り替えるべきで、変更ファイル限定を続ける理由は無くなる。これが本来の終着点
- ラチェットをすり抜ける形の違反が主流になったとき。「ファイルを新規作成すればベースがゼロなので純増になる」は正しく捕まるが、既存ファイルを大きく書き換えて違反を移送する形は検出が甘い
- `design-lint-ignore` が説明抜きで増え始めたとき。例外が常態化しているなら、規則が現実に合っていないか、ゲートが避けられているかのどちらか
