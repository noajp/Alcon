# 0014. 障害は状態ではなく遷移として報告する

2026-08-31 / el_OPS-024

## 背景

マシンのスリープ中にネットワークが切れた。その間 `ops/stall-check.mjs` は `ERROR stall-check could not read the board: fetch failed` を **1 tick ごと（300秒ごと）に出し続けた**。`ops/board-listen.mjs` も、backoff が 16 秒を超えたあとは切断のたびに1行出した。どちらも無限に続く。

報告すること自体は正しい。盤面が読めないときに「停滞なし」と黙るのは嘘になる —— 両ウォッチャーは「沈黙＝健全」を契約にしているので、見えなくなったまま黙るのは、健全であるという主張になってしまう。

問題は**同じ障害を状態として報告し続けている**ことだった。このリポジトリは既に「遷移を報告し、状態を報告しない」を複数箇所で採っている: `dev_control.paused` は flip のときだけ、停滞検知は沈黙が倍化したときだけ、リスナーの差分は変化したフィールドだけ。**障害報告だけがこの規律から外れていた。**

そしてこれは可用性の問題でもある。通知過多で監視が自動停止されれば、ノイズと一緒に**検知器そのものが失われる**。

## 選択肢

1. 障害を最初の1回だけ報告し、回復するまで完全に黙る
2. 一定間隔にレート制限する（例: 1時間に1回まで）
3. エピソード単位で扱い、**沈黙が倍化したときだけ再報告**し、回復も報告する
4. 出力は抑制せず、購読側（Monitor）で重複除去する

## 決定

3。障害は4つの遷移としてだけ現れる —— 発生 / 倍化による再報告 / **種類の変化** / 回復。

規律は `ops/faultReporter.mjs` に純関数として置き、時計は呼び出し側が渡す。`web/tests/faultReporter.test.ts` が縛る。

**障害の同一性**は、HTTP 障害ならステータスだけ、それ以外はテキストから揺らぐ部分（uuid・16進 id・時刻）を消した正規形で判定する。

**リスナーには猶予窓（15秒）**を置き、backoff 内で復帰した切断は発生も回復も報告しない。

**障害中であることは、出力の抑制とは独立にロックファイルへ書く**（`state: board unreadable for 8m — fetch failed`）。`loop-report.mjs` がそれを読み返す。

## 根拠

1 は受け入れ条件そのものに見えて、**長期障害を見えなくする**。12時間切れっぱなしのとき、唯一の1行が12時間前にあるログは、「障害が終わった」ログと区別がつかない。しかも回復を報告しないなら、その後の沈黙が健全な沈黙なのか障害なのか、後から読む人には永久に分からない。

2 を捨てたのは、**固定間隔が状態報告の言い換えでしかない**から。頻度を下げてもログの形は「同じ行が繰り返される」ままで、遷移になっていない。加えて「1時間に1回」という数字を選ぶ根拠がどこにもない。

3 を選んだのは、**盤面がこの規律を既に持っている**から。停滞検知の `Math.max(last * 2, last + 1)` をそのまま輸入した（実際に `shouldEscalate` として共有し、停滞検知側もそれを呼ぶ）。倍化は、12時間の障害を「間隔が開いていく数行」に変える —— 始まったことと、まだ続いていることの両方が残り、かつ増え方は対数。ノイズで監視が落ちる速度より、障害が長引く速度の方が遅い。

4 を捨てたのは、**購読側の重複除去は監視の外側にある**から。Monitor の設定は各セッションのもので、規律がスクリプトに無ければ、ログファイルを直接読む人・別の起動経路・将来のクラウド routine には何も効かない。規律は出力する側が持つ。

**種類の変化を別エピソードとして扱う**のが、この判断で一番間違えやすい点。`fetch failed` が `401 Unauthorized` に変わったのを「同じ障害」として黙り続けると、**権限が切れたことに気づけない** —— ネットワーク断に対して与えた沈黙を、認証断が流用することになる。同一性の線を「ステータスコード / 正規化テキスト」に引いたのは両方向の失敗があるため: 細かすぎれば request id を含むメッセージが tick ごとに別の障害に見えて元の騒音に戻り、粗すぎれば別の障害が古い沈黙に隠れる。ボディはサーバーが可変部分を置く場所、ステータスは種別を置く場所なので、そこが線になる。close code のような小さい整数は**種別そのもの**なので消さない。

**猶予窓をリスナーにだけ置いた**のは、切断の頻度が違うから。ノート PC の蓋を閉じれば socket は落ちるが、backoff 内に戻るのが普通の挙動で、それは障害ではない。発生を報告すれば回復も報告することになり、日常の1回が2行になる。逆に `stall-check` の tick は元から5分間隔で、読めなかったという事実は瞬間の揺らぎではない。

**ロックにも書く**のは、抑制の帰結が「健全に見える」ことであってはならないから。出力を止めただけなら、目が見えなくて黙っているウォッチャーと、盤面が静かで黙っているウォッチャーが同じ見え方に戻る —— それは ADR 0011 が潰した曖昧さそのもの。置き場所は既にあり（ADR 0011）、`seenAt` も動き続けるので、「生きているが見えていない」が正しく読める。

## 覆す条件

- **障害の種類が、ステータスコードでもテキストでも分けられない形で届くようになったとき。** 同一性の判定は今の2つのスクリプトが出すメッセージの形に合わせてある。構造化されたエラー（コード＋原因の型）が手に入るなら、正規化ではなくその型で判定すべき
- **ウォッチャーの tick が分より細かくなったとき。** 倍化の刻みは分で数えている。秒単位で回るものに同じ規律を当てると、最初の数回が実質毎 tick になる
- **障害中の沈黙を、ログ以外の誰かが読むようになったとき。** 今はロックの `state` が唯一の「今壊れている」の表明で、読むのは `loop-report.mjs` だけ。ディスパッチャが障害中にディスパッチを止めるべきなら、これは `dev_control` 側の話になる
- **無人稼働になったとき。** 目の前のマシンで人が見ている前提が消えれば、「1行出して黙る」の1行を誰が受け取るかが未解決になる。ADR 0005・0009・0011 と同じ条件
