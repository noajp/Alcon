# 0037 — Workload の平準化は算出し、人が適用する

## 背景

Workload は Worker ごとの負荷を稼働時間と並べて描くが、過負荷を見つけた後に「誰に渡せば収まるか」「いつに動かせば収まるか」は人が全員の週を頭に置いて解いていた。不在日に期限が来る Element、担当者のいない日付つきの Element も、チャートを読み解いた人にしか見えなかった。

この問いには盤面の数字だけで答えが出る。Element の工数と期間（`assignmentLoad`）、Worker の日ごとの稼働時間（`workerCapacity`）、Object の所属があれば、空きのある人も、前倒しで収まる日程も計算できる。

## 選択肢

- 提案の作り方：LLM（Edge Function）に盤面を渡して文章で提案させる／決定的な探索で算出し、理由を定型文で示す
- 置き場所：サーバー（RPC / Edge Function）／クライアントの純粋関数
- 適用：エージェントが自動で書き込む／人が 1 件ずつ、または一括で適用する

## 決定

- **提案はクライアントの純粋関数 `planRebalance` が算出する。** 今日から 42 日を対象に、①不在日の期限 → ②稼働超過 → ③担当者のいない日付つき作業 の順に、盤面の写しへ 1 件ずつ適用しながら貪欲に選ぶ。超過の解消は安い順に「開始を早める（期限は動かさない）」「空きのある人に渡す（同じ Object の経験者を優先）」「期限ごと後ろへずらす」で、それぞれをその人の全候補に試してから次へ進む。同じ種類の中では着手済みの作業を最後に動かすが、期限を守ることを文脈より優先し、担当替えはすべて後ろ倒しより先に試す。urgent は後ろへずらさない。新しい日付は土日を避ける。
- **プランは Space 全体でだけ出す。** 担当替えの可否は相手の負荷全体で決まるが、Domain の絞り込みや Domain・Object のタブでは範囲外の仕事が見えない。そこで出すプランは見えない予定に重ねて渡すことになる。
- **却下と絞り込みは条件として計算し直す。** 却下した提案や、絞り込んだ Worker に関わらない提案は選ばずに次の手を探す。後から除くと、残った提案が除かれた提案を前提に立ってしまう。各カードの Apply は、そのカードが前提とする先行の提案（同じ Worker か Element に触れるもの）を先に書く。
- **書き込みは人の操作でだけ起きる。** カードの Apply / Apply all が、ふだんの編集と同じ `updateElement` / `assignWorkersToElement` / `removeElementAssignee` を通す。担当替えは新しい担当者を先に加え、加えられたときだけ元の担当を外す。
- **適用前にチャートで結果を見せる。** カードにホバーすると、影響する行に適用後の負荷を線で重ねる。

## 根拠

同じ盤面からは常に同じ提案が出るので（Worker と Element は id 順に読む）、提案を検証でき、テストで固定できる。計算はブラウザで完結し、課金も通信も無い。Element 1,500・Worker 40 の過負荷の盤面で 200ms 弱かかるため、盤面が変わったときだけ計算し直す。LLM は「なぜ」の文章を滑らかにできるが、日ごとの時間の足し算を間違えれば提案そのものが過負荷を作る。数字が正しいことが先で、理由は数字から定型文で言える。

自動で書き込まないのは、担当替えが人の合意を要する変更だからである。誰が何を持つかは、本人とその上の人が納得して初めて動く。盤面の役目は黙らないことで、決めることではない（`assignmentLoad` と同じ立場）。

## 覆す条件

- **提案の根拠に数字以外（スキル・相性・本人の希望）が要る** → Worker にスキルや希望を持たせ、`bestTarget` の点数に足す。文章での相談が要るなら、算出した候補を LLM に渡して説明させる（候補の算出は変えない）。
- **盤面が大きくクライアントで重い**（盤面が変わるたびの再計算が 300ms を超える）→ 同じ関数を Web Worker かサーバーで動かす。
- **土日に働く組織で、週末を避ける提案が邪魔になる** → 稼働日（曜日・祝日）を Worker か Space の設定として持ち、`isWeekend` をその設定に置き換える。
- **人が毎回同じ提案を承認している** → その種類の提案だけ、権限内で自動適用する設定を設ける（Initiative の制約と権限の範囲で）。
