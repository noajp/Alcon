# 0010. エージェントのコメントは、名指しした相手にだけ通知する

2026-08-30 / el_STR-006

## 背景

[0003](0003-comment-notifications-in-the-database.md) は「コメントは DB トリガで通知に変える」を決め、受信者を **アサインされた Worker / Element オーナー / Domain オーナー** と定めた。購読モデルが無いことへの代用だと自覚した上での近似だった。

その近似が実際に何を生んだかが観測できた。`element_comments` は 70 件すべてが `author_kind='ai_agent'`、人間の書き込みはゼロ。Inbox には **54 行の同一文面**が並んだ。届かせるための設計が、届かなくする設計として働いている — 判断を要する 1 通が、要さない 53 通と見分けられない。

Campaign にコメント欄を足すにあたり、同じ形をもう一度書くかどうかが問われた。

## 選択肢

1. `element_comments` と同型にする（Campaign オーナーへ自動配信）
2. エージェントのコメントは通知を一切作らない
3. エージェントのコメントは `mentions` に挙がった user にだけ通知する
4. 購読テーブル（watch）を先に作り、両方をそこに載せ替える

## 決定

3。`notify_strategy_comment()` は `author_kind='ai_agent'` の行について **`mentions` の user にのみ** 通知を作る。人間が書いた行は、Campaign のオーナーと **その Campaign に既にコメントした人** へ配信する（コンテナのオーナー1点ではなく、参加の事実に基づく）。

## 根拠

1 は、噪音になると分かっている設計を、分かった上でもう一度書く行為になる。実測（54 行）がある以上「まだ問題が出ていない」とは言えない。

2 は逆に振れすぎる。エージェントが人の判断を要求する経路が消え、盤面を見に行かないと詰まりに気づけなくなる。**自走ループが人を呼べなくなる**のは、噪音より悪い。

4 が本来の解で、0003 が「覆す条件」に挙げたのもこれだった。ただし購読モデルは Element / Note / Campaign / channel の全サーフェスに関わり、この Element の範囲を大きく超える。ここで中途半端に作ると、後で本物を入れるときに剥がすものが増える。

3 は購読モデルの**最小の代用**として筋が通る。「誰に届けるか」の判断を、送り手が明示的に書く。エージェントは自分が誰の判断を要しているかを知っている唯一の存在で、それを書かせるのは負担ではなく責任の所在の明確化にあたる。人間側に広めの配信を残したのは、人の発言は宛先を書かずに投げても文脈で読まれるのが自然だから — ただしそこも「オーナーだから」ではなく「その場にいたから」に寄せた。

## 覆す条件

- **購読モデル（watch / subscribe）が入ったとき。** 受信者の決定はトリガから購読テーブルの参照に移り、この分岐ごと不要になる
- **エージェントが誰も名指ししないまま詰まるケースが観測されたとき。** 「名指しを忘れたので誰も気づかなかった」が起きるなら、`blocked` 状態の Element については名指し無しでも配信する、といった状態ベースの例外が要る。噪音を避けた結果として沈黙が生まれていないかは、Inbox ではなく**停滞検知**の側で観測する
- 人間側の「参加した人へ配信」が、長寿命の Campaign で膨らみすぎたとき。過去に一度書いただけの人が半年後も受け取り続けるなら、参加にも減衰か明示的な解除が要る
