# 0044 — AI の監査台帳は書類を持たずに記録を持ち、鎖で改ざんを示す

## 背景

AI エージェントが顧客の業務（受注の転記、請求書の受領など）を外部の実行基盤で代行するとき、経営者や管理部門は「何を任せ、何が行われ、人がどこで判断したか」を確かめたい。一方で、取引書類の中身を Alcon に置くと、漏えいの影響と保管の責任が増え、「書類を保存しない」という導入時の約束が成り立たなくなる。記録は監査に使うので、書いた本人を含め、誰も後から書き換えられないことを示す必要もある。

Alcon の `agent_runs.transcript` は会話の本文を保存する。外部の実行基盤の記録に、この形は使えない。

## 選択肢

1. `agent_runs` / `agent_actions` を拡張し、外部の実行も同じ表に入れる
2. 外部の実行は別の台帳に分け、書類は番号と鍵つきダイジェストだけを持つ。実行の結果は手順のイベントとして追記する
3. 記録は顧客のストレージにだけ置き、Alcon は表示のたびに取りに行く

## 決定

2 を採る。

- `workflow_templates`（業務の定義・版・目的・手順）、`workflow_deployments`（Space で動く導入：Domain・例外の Object・ai_agent の Worker・状態・1件あたりの想定作業時間）、`workflow_runs`（1件の書類に対する1回の実行）、`workflow_run_steps`（関節で起きたこと：接続・操作・結果・実行者）
- 実行の結果は保存せず、手順から読む（`runOutcome`）。台帳を追記だけにでき、読み方を変えても過去を書き換えずに済む
- 実行と手順は、service role を含むすべての書き手に対して UPDATE / DELETE を禁止する。例外は Space の削除によるカスケードだけで、導入の直接の削除も禁止する
- 手順は導入ごとに1本のハッシュの鎖を作る。挿入時に DB が `seq`・前の行のハッシュ・自分のハッシュを計算し、導入の行をロックして並行書き込みを直列にする。ハッシュする文字列は項目ごとに固定し、`Function/audit/auditModel.ts` の `verifyChain` が同じ形で検証する
- 実行・手順の Space と導入は、書き手の申告ではなく親の行から決める
- 読み取りは導入が属する Space のメンバーで、導入に Domain があるときはその Domain を見られる人に限る。書き込みは記録の受け口（service role）だけが行う
- 画面は Sustainment の App「Audit」とし、Workflows（導入の台帳と流れ）と Audit log（実行と手順）を持つ

## 根拠

- 1 は、本文を持つ表と持たない表の約束が混ざり、RLS も Element の可視性に縛られる。外部の業務は Element を持たない実行が大半で、合わない
- 3 は、顧客ごとのストレージ形式に表示が依存し、集計（自動完了率・差し戻し率）が遅く脆くなる。記録はメタデータだけなので Alcon に置き、求める顧客には同時に書き出す形で補える
- 鎖を DB で計算すれば、受け口や実行基盤の実装に関わらず、抜けや書き換えが鎖の切れ目として残る。画面で検証できるので、「記録がある」だけでなく「記録が欠けていない」を示せる

## 覆す条件

- 顧客が記録を自社の外に置くこと自体を拒む場合 → 3 に寄せ、Alcon は集計値だけを持つ
- 導入あたりの手順が多く、導入の行のロックが書き込みの待ちを生む場合 → 鎖を導入×日などの区間に分け、区間の先頭で前の区間の末尾を参照する
- 外部の実行と Alcon 内のエージェント（`run-agent`）を同じ画面で監査する必要が出た場合 → `agent_runs` を本文なしの形でこの台帳に写すか、両方を読む表示に広げる
