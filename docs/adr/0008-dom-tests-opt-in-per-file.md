# 0008. DOM テストは設定分割ではなくファイル単位の opt-in

2026-08-30 / el_OPS-017・PR #215

## 背景

vitest は意図的に `environment: 'node'` のみで構成されていた（el_OPS-011）。設定のコメントは「DOM が要るテストが出たら jsdom を足せ、今ではない」と明記していた。

その「今」が来た。`el_UXQ-009` で QuickAdd の Enter の挙動を変えたが、**それが動くことを確かめる手段が1つも無かった**。tsc は通る。design-lint も通る。**1件ごとに閉じるという直そうとしているバグそのものに対しても、両方通る。** dev サーバーはサインインを要求し、資格情報を扱わないセッションでは画面に到達できない（risk register R4）。

つまり **UI の挙動変更を検証する手段がゼロ**だった。

## 選択肢

1. `vitest.config` を2つに割る（node 用と jsdom 用）
2. vitest の `projects` / workspace 機能で環境ごとに分ける
3. 既定を node のまま、DOM が要るテストが自分の docblock で `@vitest-environment jsdom` を宣言する

## 決定

3。`include` を `.tsx` まで広げ、環境の既定は node のまま。DOM が要るファイルだけが先頭で宣言する。JSX の変換設定は不要（esbuild が tsconfig から読む）。

## 根拠

**設定ファイルが1つなら同期がずれない。** 割ると alias・include・環境の定義が2箇所になり、片方だけ直す事故が必ず起きる。

jsdom の起動コスト（実測で数百 ms）が**要求したファイルにだけ乗る**。大半のテストは純粋ロジックで document を読まないので、全体を jsdom にするのはただの遅延。

そして宣言がファイルの先頭にあるので、**そのテストが何を必要としているかが読めば分かる**。設定ファイルの glob を追いに行かなくていい。

元の構成の「最小に保つ」という意図は、拡張しても壊していない。増えた devDependency は jsdom / @testing-library/react / user-event の3つで、環境の既定は変わっていない。

## テストが意味を持つことの確認

書いたテストを `origin/main` に対して走らせると **8件中4件が落ちた** — このブランチが導入する挙動を記述した、まさにその4件。残る4件は新旧で挙動が一致するので両方で通る。

これを記録するのは、**コードの現状をなぞるだけのテストを書いてしまうのが最もありふれた失敗**だから。落ちるべき時に落ちることを一度でも確かめていないテストは、通っていることに意味が無い。

## 覆す条件

- DOM テストが大半を占めるようになったとき。既定を jsdom にして node 側が opt-in する方が、宣言の総数が減る
- 環境ごとに setup ファイルや異なる alias が要るようになったとき。docblock は環境しか切り替えられないので、そこを越えたら選択肢2（projects）が必要
- コンポーネント境界を越える検証（呼び出し側との結線、実際の描画）が主要な関心になったとき。それはこの仕組みでは届かない領域で、E2E かサインイン可能な検証環境の話になる。**`el_UXQ-009` の「作成のたびにリストへ即時反映」は、まさにここに落ちてコード読解で確認するしかなかった**
