# 0027 — Agents act on Elements with the caller's RLS and stop for approval before external writes

## 背景

ユーザーは、起票された Element を AI が実行して作業を代行する仕組みを、製品として完成させることを求めた（ELE_AI-094）。代行は成果物を作ることに限らない。「メールに 100 件返信する」なら、実際に返信できればよい。参考にしたのは CopilotKit/OpenDots で、取り入れた考え方は次のとおり。役割・指示・使えるツールを持つ専門エージェント、ページ（Alcon では Element）に結び付いた作業スレッド、保存や送信の前の人による承認、ツール呼び出しの実況表示、資格情報はサーバー側だけに置くこと。

既存の `run-agent` は、計画・作業ログ・サブ要素の完了・成果物のコメントまでしかできず、盤面や外部サービスを操作する道具を持っていなかった。しかも service role で動き、呼び出した人の権限を確かめていなかった。`agent_runs` / `agent_run_steps` の RLS は、ログインしていれば誰でも全件を読み書きできた。

## 選択肢

- 実行基盤：Managed Agents（Anthropic が実行と隔離環境を持つ）／Claude API と自前のループを Edge Function で回す
- 権限：service role で動かし、アプリ側で可視性を確かめる／呼び出した人の JWT で動かし、RLS に任せる
- 承認：書き込みのたびに 1 件ずつ承認する／同じターンの書き込みをまとめて 1 回の承認にする／承認しない
- 長い作業：1 回の実行に収める／経過（transcript）を保存して、続きを自分で再開する
- 成果物の置き場所：Note（作成者本人だけが見られる）／Element に紐づく専用テーブル

## 決定

- **自前のループを Edge Function `run-agent` で回す。** モデルは Claude API（既定は `claude-sonnet-5-5`、Worker の `ai_config.model` で `claude-haiku-4-5` / `claude-opus-5-5` を選べる）。ループの判断（`loop.ts`）は I/O を持たない純粋なモジュールにして、テストで固定する。
- **盤面・成果物・連携の一覧は、呼び出した人の JWT で読み書きする。** RLS が、その人に見えるものとできることを決める。service role は、実行自体の記録（状態・経過・使用量・手順・承認依頼）と、Vault からの資格情報の読み出しにだけ使う。ブラウザからできるのは、queued の実行を作ることと、まだ動いている実行を止めることだけ（列単位の権限とトリガで強制する）。こうすることで、メンバーが自分の実行の費用を書き換えて予算を逃れることはできない。エージェントは実行を始めた人として動くので、開始・承認・却下・再開ができるのも、その人だけにする。Element を見られる他の人は、経過を見て止めることだけができる。
- **外部への書き込みは承認を通す。** 同じターンで呼ばれた書き込みは、1 件の `agent_actions` にまとめる。承認は、提示した入力の SHA-256 に結び付ける。内容が違う決定や、もう処理済みの決定は、実行に触れる前に断り、実行は待ち続ける。連携の委任レベルが `full_delegation` なら、承認なしで実行する。連携先の読み取りと、Alcon 内（RLS の範囲内）の書き込みは、承認なしで行う。
- **完了は、任務の達成とその根拠で示す。** 最後に必ず `finish`（completed / partial / blocked）を呼び、完了報告を Element にコメントとして残す。completed なら Element を review に、blocked なら blocked に移す。成果物が要る任務では、`save_artifact` で `agent_artifacts` に保存する。成果物は、Element を見られる人なら誰でも読める。
- **長い作業は区切って続ける。** 1 回の実行は 14 ターン / 110 秒で区切り、同じ人の JWT（メモリ上で受け渡し、保存しない）で続きを起動する。続きは 1 回限りのトークンで claim するので、同じ実行が並んで二重に走ることはない。経過はターンごとに保存する。承認された書き込みも 1 件ごとに進み具合を保存し、時間が切れたら続きの区切りで残りを実行する。古い道具の結果は、context editing（`clear_tool_uses`）で文脈から外す。道具の定義は最初の区切りで固定し、後の区切りでも同じ prefix を送る（thinking block がその prefix に結び付いているため）。セッションが切れたら `paused` にし、その人が開いたときに再開する。エラーで止まった実行や、応答が 5 分途絶えた実行は `paused` 扱いになり、始めた人が再開できる。
- **経過はブラウザに出さない。** transcript には、始めた人の権限で読んだ道具の結果がそのまま入る。そのため、`transcript` と続きのトークンは、ブラウザから select できない列にする。閲覧者に見えるのは、手順（steps）、承認依頼、完了報告、成果物だけ。
- **費用には上限を設ける。** 応答ごとにトークン量と費用を `agent_runs` に記録し、Space ごとの月の上限（`ai_monthly_budget_usd`、既定 $20）に達したら止める。Space に属さない Element では、始めた人ごとの月の上限（$20）を使う。どちらの場合も、1 回の実行は $5 で止める。
- **外部連携は Space 単位で登録する（`integrations`）。** MCP（Streamable HTTP）と HTTP API の 2 種類。資格情報は Vault に置き、オーナーは `set_integration_secret` で書き込み、`get_integration_secret` は service role しか実行できない。秘密情報は Vault の名前（`integration:<id>`）で引き当て、行の `secret_id` は信用しない。`secret_id` と `last_test` はブラウザから書けない。接続先は https の公開ホストに限り（私設・ループバック・リンクローカル・ベンチマーク用の IPv4、すべての IPv6 リテラル、内部名は拒否）、HTTP API のパスが登録した base URL の外に出ることはない。MCP の道具が読み取りかどうかは、リモートの `readOnlyHint` に従う。

## 根拠

Managed Agents は、実行と隔離環境まで任せられる。ただ、Alcon が必要としているのは、Alcon 内の RLS と承認・監査を通す道具であり、隔離環境での任意のコード実行ではない。また、資格情報と承認の境界を自分たちのデータベースで握る必要がある。自前のループなら、既存のボードツール（Copilot・MCP と共有）をそのまま使え、承認待ちで止めて再開する制御も素直に書ける。

service role で動かすと、可視性の判定をアプリ側ですべて正しく書き続ける必要があり、1 か所の漏れが他人のデータの書き換えになる。呼び出した人の JWT なら、アプリ本体と同じ RLS がそのまま境界になる。

1 件ずつの承認は、大量の作業（100 件の返信）では使いものにならない。承認しない設計は、取り消しにくい外部への書き込みを人の意図の外に出してしまう。そこで「同じターンの書き込みをまとめる」を既定にし、信頼できる連携だけを全委任にできるようにした。

Note は作成者本人しか見られないので、チームで確かめる成果物の置き場所にならない。

## 覆す条件

- 1 回の実行に収まらない作業が、区切り（14 ターン / 110 秒）と続きの起動では回らないほど多くなったら、キューとワーカーによる実行（pg_cron や外部のワーカー）に移す
- 隔離環境でのコード実行やブラウザ操作が必要な任務が実際に増えたら、Managed Agents や computer use を道具として足す
- 「同じターンの書き込みをまとめる」では承認の粒度が粗すぎる、あるいは細かすぎるという指摘が出たら、計画単位の承認や、件数のしきい値による自動承認を設計する
- 予算の単位が Space では合わなくなったら（エージェント単位・Initiative 単位など）、上限の持ち方を見直す。予算は区切りの開始時に読むので、並行する実行が N 本あれば、最大で N × $5 まで上限を超えうる。これが問題になったら、DB 側で予約（reserve）してから呼ぶ方式に移す
- 承認された書き込みは「少なくとも 1 回」実行される（実行した直後、進み具合を保存する前に区切りが打ち切られると、再開時にもう一度実行する）。二重に実行されて困る連携（送金など）が出てきたら、冪等キーを連携側に渡すか、送信前に記録する
- Worker が Space 単位で絞られたら（ELE_QLT-090）、エージェントの選び方をその境界に合わせる
- 信頼できない MCP サーバーが、書き込みに `readOnlyHint` を付けて承認を逃れる例が出たら、連携ごとに「ヒントを信用する」の設定を設け、既定ではすべての道具を書き込みとして扱う
- DNS で私設アドレスに解決されるホスト名（DNS rebinding）が実際に問題になったら、接続前に名前解決して宛先のアドレスを確かめる
