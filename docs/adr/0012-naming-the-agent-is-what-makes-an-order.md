# 0012. Campaign のコメントは、エージェントを名指ししたときだけ指示になる

2026-08-31 / el_STR-007

## 背景

ユーザーの要求（2026-08-30）は「自分はこれらの指示を Friction の Campaign をみて、そこに指示を出すだけで完結させたい」。

この経路は**片方向しか設計されていなかった**。上向き — 実行の事実が Campaign に届く — は `element_comments`・`dev_events`・リスナーで組んである。下向き — Campaign に書いた意図が仕事になる — は存在しない。[0010](0010-agents-notify-only-who-they-name.md) で Campaign にコメント欄はできたが、書いたものを読む側がいない。`ops/board-listen.mjs` は `strategy_comments` を購読していなかった。

購読を足すと、次の問いが**必ず**出る。**Campaign に書かれた文のうち、どれが指示か。**

Campaign のコメント欄は、そもそも「意図を腐らせないため」に作った（migration `20260830000005`）。「この前提はもう成り立っていない」を、前提の隣に、前提を破壊せずに書ける場所。**そこに書いたものが全部仕事になるなら、その場所は消える。** 考えるために書いた行が、書いた瞬間に着手される。

これは差分抽出の設計で一度却下した失敗と同じ形をしている。**「問い」を「やること」に変換すると、答えは常に「やる」に倒れる。**

## 選択肢

1. Campaign の人間コメントを全て指示として扱う
2. 記法を新設する（`▶ ● ⬆ ✔ ■` に倣った指示用のグリフ、例 `▷ 指示`）
3. 構造で持つ（`strategy_comments.kind` 列、あるいは `directives` テーブル）
4. **エージェントを名指ししたコメントだけを指示とする**（`@Claude` の本文テキスト）
5. 名指しを既存の `mentions uuid[]` 列で表現する

## 決定

4。加えて往復の形を次のように定める。

- **指示**（人 → エージェント）: Campaign のコメント本文が `@Claude` を含む
- **提案**（エージェント → 人）: 同じスレッドに `◆ 提案`。盤面には**何も書かない**。番号付きで1行1 Element（Object の prefix / タイトル / 意図 / 受け入れ条件）
- **承認**（人 → エージェント）: 次の名指しコメント。「1 と 3 を」「全部」「2 は要らない」。**承認は指示の一種**であって別の記法を持たない
- **起票**: 承認された分だけを起票し、`✔ 完了` で display_id を返す

`■ Blocked` は Campaign スレッドでも意味を変えない — 指示を提案に変換できないとき（曖昧・スコープ外）に使う。

`◆ 提案` 以外に新しい語彙は増やさない。`✔` `■` は `element_comments` と同じ意味のまま、置き場所が増えるだけ。

リスナーは `ORDER`（名指しあり）と `CAMPAIGN`（名指しなし）を別の行として出す。`ORDER` は**盤面のスコープ外の Campaign からも報告する**。

## 根拠

**1 を捨てた理由が、この判断の本体。** 全てを指示にすると、Campaign が「意図を保つ場所」から「作業キュー」に変わる。上に書いた通り、それは `strategy_comments` を作った理由そのものを消す。人が人に向けて書くこともできなくなる。

**2（グリフ新設）は、書く人を間違えている。** `▶ ● ⬆ ✔ ■` はエージェントが SQL で書く記号で、タイプしやすさは問題にならない。**指示は人間が textarea に手で打つ。** キーボードから出せない記号を要求する規約は、誰も使わないので存在しないのと同じ。そして `@名前` は同じ入力欄の mention ピッカーに**既にある** — 意味も「あなたに向けて言っている」で完全に一致する。無いものを発明する前に、あるものが既に答えている。

**4 は [0010](0010-agents-notify-only-who-they-name.md) の鏡像**で、そこが効いている。0010 は「エージェントは名指しした相手にしか届かない」。ここは「人はエージェントを名指ししたときだけ届く」。**規則は1つで、両方向に効く。** 覚えることが増えていない。

**3（構造で持つ）は概念を増やす。** `CLAUDE.md` の「業界語彙に依存しない少数概念」に反する。列やテーブルを足せば migration と UI がついてくるし、承認のためにもう1つ必要になる。テキストが既に表現できているものを、スキーマに昇格させる理由が無い。

**5（`mentions` 列で名指し）は、実際に壊れる。** `mentions` の uuid はトリガで `notifications.recipient_id` に入り、そこは `auth.users` への FK。AI Worker（`type='ai_agent'`）に auth user は無いので、その id を入れた INSERT は失敗する — **エージェントを名指しした瞬間にコメントが投稿できなくなる。** 加えて `StrategyCommentsPanel` の mention ピッカーは `type === 'human' && user_id` で絞っており、`extractMentions` も同じ条件なので、`@Claude` は**どの経路を通っても本文テキストのままになる**。テキストで受けるのは妥協ではなく、唯一動く経路。

**自動パースして Element を直接起票しない**のは、この Element が最初から持っていた判断。`◆ 提案` の1往復はその判断の実体で、往復を消せば 1 に戻る。ユーザーの負担は増えていない — Campaign を見ているだけで済む、という要求は満たしている。

**承認に記法を与えなかった**理由は2つ。人間側が覚えるものが1つで済むこと。そして承認・修正・新しい指示の区別は**スレッドの順序が既に持っている**ので、構文で作り直すと二重管理になること。

**`ORDER` をスコープ外の Campaign からも出す**のは、`elements` の扱い（Friction Dev ドメイン以外は捨てる）とわざと違えている。雑談はスコープで切ってよい — 他ドメインの雑談は自走ループの仕事ではない。しかし**失敗の形が沈黙になる規約は壊れている**。名前を打った人には、行が捨てられたのか、エージェントが読んで動かないと決めたのかが区別できない。リスナーは報告するだけで強制しない（[0005](0005-event-driven-loop.md)）という分担のまま、判断の機会だけをエージェント側に残す。

## 覆す条件

- **`◆ 提案` に誰も返事をしないまま溜まったとき。** 承認が「次の名指しコメント」であることは、承認しないことのコストをゼロにしている。放置された提案が積むだけになったら、提案に期限か明示的な棄却が要る。観測点は Inbox ではなく、**提案を出した Element が `blocked` のまま何 tick 動かないか**（[0007](0007-waiting-is-blocked-not-in-progress.md)）
- **`@Claude` の名指しが誤検知を生んだとき。** 今は本文の部分一致で、引用や振り返り（「@Claude と書けばいい」）も指示になる。エージェント自身の行は `SELF_AUTHOR` で落ちるので自己ループにはならないが、人が書いた引用は拾う。実際に起きたら、行頭に限定するか、ピッカーが挿入した位置を構造で持つ話に戻る（つまり 3 が正しくなる）
- **AI Worker が auth user を持つようになったとき。** 5 を捨てた根拠が消え、名指しは `mentions` に統合できる。テキストと uuid の二重表現が無くなるので、そのときは移すべき
- **Campaign を指令所として使う人が複数になったとき。** 「エージェント」が1体である前提で `@Claude` を書いている。複数のエージェント、あるいは誰の指示か区別が要るようになれば、名前だけでは足りない
- **エージェントが提案を出さずに起票したとき。** 規約違反ではなく、規約が現実に合っていない兆候として読む。「明らかに起票するだけ」の指示が多いなら、提案を省ける条件を規約に書くべきで、破られた規約を放置すべきではない
