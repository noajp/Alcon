# 0009. ループの起動をセッションではなく hook に持たせる

2026-08-30 / el_OPS-018

## 背景

ADR 0005 でループはイベント駆動になった。盤面の変化は `ops/board-listen.mjs` に即座に届き、`ops/stall-check.mjs` が「working と名乗ったまま黙っていないか」だけを見張る。**どちらも main にあり、どのセッションからでも実行できる。**

しかし実際に動いていたのは、**あるセッションが手で Monitor に載せた1つだけ**だった。そのセッションが死ねば止まり、他のセッションでは最初から動いていない。

これが痛いのは、ADR 0005 が作った性質そのものを無効化するからだ。「カードを動かすことがそのまま指示になる」のは、リスナーが動いている間だけ成立する。そして**リスナーが止まっている盤面は、何も起きていない盤面と見分けがつかない。** 指示が届かなかったことに、指示した側も受ける側も気づけない。

同時に、素朴な解決は別の壊れ方をする。このマシンでは常時3つのセッションが並走している。全セッションが起動すれば、盤面の1変化が**3通の同一通知**になる。その倍率が続けば監視は黙らされ、黙らされた監視は動いていないのと同じになる。

## 選択肢

1. 今まで通り手で起動する
2. SessionStart hook で毎セッション起動する（多重起動を許容）
3. SessionStart hook で毎セッション起動し、リポジトリ単位のリースで1つに絞る
4. launchd 等でマシンに常駐デーモンを入れる

## 決定

3。`.claude/settings.json` の SessionStart hook が両方を無条件に起動し、`ops/singleLease.mjs` がどれが実際に走るかを決める。リースが取れなかったプロセスは**無出力で exit 0** する。

## 根拠

1 を捨てたのは、起動が人間の記憶に依存するから。忘れても何も起きず、忘れたこと自体が観測できない。**失敗が沈黙として現れる仕組みは、失敗しないことを前提にできない。**

2 を捨てたのは上記の3倍通知。ここは実測で確かめた — リース無しなら12プロセス同時起動で12個が全部生き残る。

4 を捨てた理由は2つ。まず launchd はセッションの有無と無関係に動くので、**スコープ外の無人稼働に片足を踏み入れる**（そこには課金判断が要る）。加えてマシン個別の設定なので、リポジトリをチェックアウトした他の環境には何の効果もない。`.claude/settings.json` はリポジトリに入るため、**全チェックアウト・全 worktree で同じことが起きる**。ループの起動条件がコードと一緒にバージョン管理されるのは、それ自体が価値になる。

リースをリポジトリ単位にしたのは、**worktree は別ディレクトリだが同じ盤面を見る同じプロジェクト**だから。ワーキングディレクトリ単位では worktree の数だけリスナーが立つ。キーは `git rev-parse --git-common-dir` から作る — 全 worktree で同じ値になる唯一の識別子で、これを**プロセスの cwd ではなくスクリプト自身の位置から**引く。hook はどこから起動するか分からず、cwd 基準にすると同じスクリプトの2つの起動が別の名前空間に落ちて両方走る。

排他の原子性は `link(2)` に置いた。「読んで、居なければ書く」では2プロセスが同時に「居ない」を見て両方が勝つ。`link` は存在すれば EEXIST で失敗するので、何プロセスが同じ瞬間に起動しても勝者はちょうど1つになる。ペイロードを先に書いて後から link するのは、**敗者がそのファイルを読んで諦めを判断する**以上、半端な内容が観測されてはいけないため。

生存確認は `kill(pid, 0)`。クラッシュした保持者が残したロックは**次の起動者が引き取る**ので、事故が「ループが二度と立たない」に化けない。

無出力で終わる設計は hook の前提そのもの。毎セッション必ず走る以上、**常態で1行でも出せばそれは全セッションに配られるノイズ**になる。同じ理由で、service role key が無い時も hook 経由なら黙って exit 0 する。ただし人が手で叩いた時は今まで通り理由を説明して exit 1 する（`FRICTION_LOOP_HOOK` で切り替え）。**設定の不在は黙り、障害は喋る** — 鍵が無いのはこのマシンがループ用に設定されていないというだけで、報告すべき異常ではない。一方、鍵はあるのに盤面が読めないのは異常なので、そちらは hook 経由でも喋る。

`--once` だけはリースを取らない。あれは監視ではなく質問で、走っている監視に遠慮して黙る `--once` は、人が「何か詰まってる?」と訊くために打つ唯一のコマンドが何も答えない状態になる。

## 覆す条件

- **通知の配送が hook では成立しないと実測されたとき。** ここが今いちばん薄い。hook が保証するのは「プロセスが動いていること」までで、その stdout はログファイルに落ちるだけ。Monitor に載せた時のように**行が通知にならない**。「ループが動いている」と「人が気づける」は別の問題で、後者はまだセッションが手でログを追う必要がある。運用してみて気づけないなら、hook は起動係に留め、通知経路そのものを別に設計する
- **リースの粒度が粗すぎると分かったとき。** 今は「1リポジトリにリスナー1つ」。worktree ごとに別ドメイン・別盤面を見る使い方が出てきたら、キーをリポジトリからドメインに変える
- **セッションが死んだあとの子プロセスが害になったとき。** 今は孤児が残ってもリースが stale を回収するので事故にはならないが、溜まって実害が出るなら SessionEnd で明示的に落とす形にする
- **無人稼働が要件になったとき。** hook はセッションが1つも開かれなければ何も起こさない。ラップトップを閉じても回す必要が出た時点で、この判断ごとクラウド routine に置き換わる（ADR 0005 と同じ条件）
