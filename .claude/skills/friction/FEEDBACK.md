# FEEDBACK — 外部チームの声を捌く

読むのは **Friction Dev 以外の盤面から声が届いたとき**だけ。通常運転には要らない（原則8）。

## 何がフィードバックか — 名指しがそれを決める

ORDER と同じ規則（→ ADR [0012](../../../docs/adr/0012-naming-the-agent-is-what-makes-an-order.md)）。**エージェントを名指ししたコメントだけが我々宛て。**

他チームの盤面には彼ら自身の仕事の会話が流れている。それは我々の business ではない。読まないのは規模の都合ではなく規律で、全部を読めば彼らの作戦会議がこちらの通知になり、判断材料が薄まり、彼らの側から見れば監視される。

代償ははっきりしている: **規約を知らない人のフィードバックは黙って死ぬ。** だから受け口は一度だけ相手の Initiative に書いて知らせる。沈黙で失敗するプロトコルは壊れている。

## 妥当性の判断 — 4つの問いを順に

### 1. 状況が書かれているか、評決だけか

「見づらい」「使いにくい」は評決であって観察ではない。**何をしようとして、何が起きて、どう困ったか**が無ければ、欠陥と好みを区別できない。無ければ**起票せず問い返す**。

ここを飛ばすと、間違った理由で正しい場所を直すことになる。

> `el_UXQ-021` は「ボタンとかソートの醜さ」として起票された。実装して分かった実際の欠陥は **26px の裸の矢印で、ツールチップがどの列でソートしているか言っていない**ことだった。項目数の問題は既に解決済みだった。**起票理由の方が間違っていた。**

### 2. 判断が変わったか、不快なだけか

Friction は意思決定支援の製品なので、**判断を変えた摩擦は欠陥**。「決められなかった」「間違った方を選んだ」「見落とした」は最優先。

不快なだけのものも妥当だが、それは品質項目であって欠陥ではない。同じ箱に入れると、緊急でないものが緊急なものを埋める。

### 3. 概念モデルと矛盾しないか

矛盾する要望は**起票しない。答えを返す。** Object のネスト（廃止済み）、「Task」と呼ぶ（Element が業界横断の抽象名）、Strategy と Execution を1つのリストに（意図と投入の区別が崩れる）——これらは仕事ではない。

ただし**矛盾する要望はたいてい、本当の必要が違う服を着ている。**「Object をネストしたい」は「この5つがひとまとまりだと言いたい」かもしれず、それは Initiative か Phase か Property で満たせる。だから答えと一緒に**何をしようとしていたかを訊く**。

ここが最も価値が高く、最も取り違えやすい。**モデルを守ることと、要望を却下することは別。**

### 4. 既に盤面にあるか

あれば合流させ、既存の display_id を返す。二重起票しない（原則1）。

## 結末は5つ。沈黙は無い

| 結末 | 返すもの |
|---|---|
| 起票 | display_id。原文を引用して Element に残す |
| 既存に合流 | 既存の display_id |
| 問い返す | 何が足りないか |
| 答えて起票しない | 答えそのもの（モデルとの矛盾 / 設定の問題） |
| 保留 | 理由と、**何が起きたら復活するか** |

**必ず来た場所へ返す。** 5つ目まで含めて、返事の無い結末は無い。

## 返信が届かないことがある

エージェントのコメントは **`mentions` に入れた相手にしか届かない**（→ ADR [0010](../../../docs/adr/0010-agents-notify-only-who-they-name.md)）。`mentions` は `auth.users` の uuid。

**返信相手は「Element の担当者」ではなく「そのコメントを書いたアカウント」。** `workers.user_id` が null の Worker はアカウントを持たない。アサインはできても通知は届かず、担当者に返したつもりで誰にも届かない、が起きる。書く前に確認する。

## 優先度

外部チームの声は**自家生成でない唯一の証拠**なので、自分の UI 監査より重い。ただし自動的に最上位ではない。内容が正当化する優先度で入れ、親指を1つだけ乗せる:

**判断が止まった報告は最低でも `high`。**
