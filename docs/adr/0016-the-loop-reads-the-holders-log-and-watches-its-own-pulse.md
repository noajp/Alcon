# 0016. ループを止めない — 受信は保持者のログの tail、時計は自分の死活、無人稼働は scheduled task

2026-09-03 / ELE_DEC-001

## 背景

ADR 0005 でループはイベント駆動になり、ADR 0009 で hook がリスナーを起動するようになった。しかし hook が起動したプロセスは stdout を捨て、**イベントを通知として受け取るセッションがどこにも無い**構成になっていた。リースはリポジトリ単位で1つなので、保持者は当事者セッションの子とは限らない — 2026-09-03 の実測では、別 worktree の hook 子プロセスがリースを持ち、走っている3セッションのどれも盤面の変化を受けていなかった。盤面は動いているのに、誰も見ていない。

同日、ユーザーから「自律開発のループを延々に回し続けたい」という要求があった。

## 選択肢

1. リースを奪い、自分のセッションが Monitor 配下でリスナーを走らせる
2. 保持者が書いているログを Monitor で `tail -F` する
3. リスナーをセッションごとに起動する（ADR 0009 が多重通知を理由に捨てた案）
4. マシンに常駐デーモンを入れる（ADR 0009 が捨てた案）
5. scheduled task で新しいセッションを定期起動し、セッションが閉じていても盤面を拾いに来る

## 決定

2 を受信の既定にする。加えてセッションの中に**自分の死活**を見る時計を1つ置き（CronCreate、40 分前後）、「走行中エージェントが無く、着手できる Element がある」ときだけ次を取る。**ターンを空で終えない**ことを規約にする — 着手できる仕事が残っているのに、走行中エージェントも Monitor も無い状態でターンを閉じない。

5 は課金と権限（scheduled task の作成はユーザー自身の発話が要る）を伴うので、DEC の判断（ELE_DEC-001）を経てから入れる。承認されるまでの守備範囲は「セッションが生きている間の即応」。

## 根拠

- 2 は保持者を殺さない。1 は相手の worktree のリスナーを止めるので、そのセッションが hook 経由で持っていた（潜在的な）受信を奪う。ログは1ファイルで、何セッションが tail しても保持者に影響が無い
- セッション内の時計は原則2「時計は死だけを検知する」の派生。仕事を探すのではなく、**自分のループが途切れたこと**（イベントを取りこぼした、ターンを空で閉じた）を検知する。健全なら無出力
- 「ターンを空で終えない」は、この harness ではターンの終了がループの終了と同義だから。エージェント完了と Monitor の通知だけがターンを再開する
- 5 が ADR 0006 を破らないことは確認した。scheduled task はこのマシンでローカルに走り、service role を外に出さない
- 3・4 を捨てた理由は ADR 0009 のまま

## 覆す条件

- ログの truncate / 上限でイベントを取りこぼすと実測されたら、tail をやめて realtime を直接読む（通知としてだけ使い、データ源にはしない）
- scheduled task が承認されて安定したら、セッション内の時計は冗長になる。片方に寄せる
- 複数セッションが同じイベントに反応して二重着手が起きたら、着手コメントをリースにする（el_TRJ-012）を先に入れる
