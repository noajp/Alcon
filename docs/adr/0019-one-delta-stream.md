# 0019. サーバーが確定した変更は 1 本の差分ストリームで受ける

2026-09-04 / フロントエンド高速化（ADR 0018 の続き）

## 背景

ADR 0018 で共有データを query cache に載せた結果、「変更がどう画面に届くか」が 3 経路に分かれた。自分の書き込みは楽観更新、他所からの変更は表ごとに手書きした realtime 購読の invalidate、それでも取りこぼす分は staleTime 切れの再取得。整合性は「全経路 × 全表の配線が揃っている」ことに依存し、PR #313 のレビューで出た 8 件のうち 5 件は書き込み側の invalidate 漏れだった。書き手が人か AI Worker か CI かは関係なく、配線の掛け算そのものが事故の温床になる。

## 決定

- **ingress は 1 本。** `alcon/sync/deltaStream.ts` がワークスペース形の全表を 1 チャネルで購読し、届いた行を正規化キャッシュへ差分として当てる。Element の UPDATE はその Element が居るすべてのキャッシュを patch、Subelement / 担当 / コメント / リアクションは親に着地、コメントの INSERT は活動ロールアップも進める。所属（multi-homing / edge / Property 定義）のように行ではなく集合が変わるものは、同じ場所から該当キーを invalidate する
- **patch は純粋関数。** `alcon/sync/explorerPatch.ts` は I/O を持たず、触れなかった参照を必ず保つ（no-op は同一参照を返す）。楽観更新と差分ストリームはこれを共用し、`tests/` で振る舞いを固定する
- **表ごとの購読は持たない。** データフックは読むだけで、realtime を知らない。新しい表を足すときは deltaStream の表リストと publication migration に 1 行ずつ足す
- **楽観更新は前借り。** 書き込みはキャッシュへ先に当ててよいが、確定は差分ストリームから戻ってくる行で行う。書き込み側は invalidate を書かない（例外: 差分が届かない集合の変化）
- **publication は migration で管理する。** 購読している表が `supabase_realtime` に無いと黙って届かない。`20260904130000_workspace_realtime_publication.sql` が全表を冪等に足す

## やらないこと

ローカル DB を真実にすること、オフラインの書き込みキュー。効く条件（同時編集者が複数 / 不安定な回線 / Domain あたり数千 Element）が今は無く、RLS の 4 スコープと multi-homing をクライアントに二重実装する代償に見合わない。条件が来たら、この差分ストリームの下に永続化とキューを足す。

## 覆す条件

- Supabase Realtime が RLS 越しの配信をやめる、または DELETE に主キー以外を載せるようになる（削除の探索が不要になる）
- 上の「やらないこと」の条件が実際に起きた（そのときはこの決定を拡張する側に倒す）
