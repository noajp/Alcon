盤面に仕事が無いとき、仕事を探すのではなく**作戦を回す**。

Friction は Strategy & Execution の SaaS なので、Friction 自身で架空の作戦や事業を運用できる。運用すれば必ずどこかで詰まる。**その詰まりが次に作るものの唯一信頼できる情報源**であり、機能一覧を眺めても、ユーザーに要望を聞いても、同じものは出てこない。

実装ループ（盤面から取って PR にしてマージするまで）の規約は friction スキル（`.claude/skills/friction/SKILL.md`）。こちらはその**上流** —— 盤面に何を載せるかを決める側。

## なぜ効くのか

監査ではなく**使用**だから。

「Campaign 画面に何が足りないか」を検討しても出てこないが、燃料供給網が途絶して指揮官が決断を迫られた瞬間に「決断を書く場所が無い」ことは避けようがなく分かる。**架空でも作戦は容赦がない。**

そして機能を入れると、その機能を使ったときにしか見えない次の摩擦が出る。「決断を書けるようにした」→ 使う →「見直した結果を書けない」→ 実装 → 使う →「見直し済みが見直し待ちに居座る」。一度に設計しきろうとしても出てこない連鎖で、これが駆動の本体。

## 演習の設計

**盤面に実データとして作る。** Domain 1つ、Phase を数個、部隊や部門にあたる Object を4〜6、任務や施策にあたる Element を8〜16。Worker は架空の人物。すべて `【架空演習】` と description に明記する。

守ること:

- **前の演習の AAR が名指しした未解決の類型を狙う。** 思いつきで作らない。前回「Phase に完了が無い」「可用性に時間軸が無い」と分かったなら、次はそれが痛む設計にする
- **危機を仕込む。** 順調な計画は何も暴かない。供給の途絶、需要の超過、キーパーソンの離脱、期日の後ろ倒し。**明示した前提を途中で壊す**のが最も効く
- **制約の種類を変える。** 軍事シナリオでは物資と時間が制約になり「全員が全力」が自然だが、企業シナリオでは人そのものが制約になる。同じ機能が違う壊れ方をして、同じ症状のより深い原因が見える
- **小さく保つ。** 16 Element で足りる。大きくすると演習の維持自体が仕事になり、観察が薄くなる
- **Campaign の description に「崩れたら知りたい前提」を明示する。** 後でそれを壊すため

## 1サイクルの形

**進行 → 観察 → 疑問 → 仮説 → フィードバック。** 毎回この順で、飛ばさない。

1. **進行** — 作戦を1日分または1週分進める。Element の status と progress を動かし、コメントで何が起きたかを書く。ここで手を抜くと観察が出ない
2. **観察** — 盤面を**実際に見て**、何が見えて何が見えないかを書く。SQL で数えられるものは数える（Phase ごとの完了率、Worker ごとの負荷、blocked の件数）。「見えるはずのものが見えない」は数字で示す
3. **疑問** — **「なぜこうなっているのか」を問う。「これが足りない」と書かない。** ここが手法の核心。「Campaign にリスクペインが無い」は要望だが、「なぜ遅行指標（完了率）だけで先行指標が無いのか？ 完了率 0% は未着手と詰まっているを区別しない」は設計の手掛かりになる
4. **仮説** — どう直すか。**既存の設計を先に読む。** この盤面では「機能が無い」と感じた箇所の実装が既にあり呼び出し元だけが無かった例が4件出た。新しいテーブルを足す前に既存の列と関数を探す
5. **フィードバック** — 所見を Element として起票し、SITREP を Campaign のコメントに出す

## 所見の起票

**摩擦を感じたその場で Element にする。** 後でまとめない。忘れるからではなく、**痛みの文脈が失われる**から。

description の型:

```
## 観察（<演習名> Cycle N）
何が起きて、盤面が何を見せ、何を見せなかったか。数えたなら数字を入れる

## 疑問
なぜそうなっているのか。要望ではなく問い

## 既にあるもの（調査した場合）
関連する既存のテーブル・関数・コンポーネント。「先に読め」と書く

## 仮説
直し方の候補。最小案を必ず含める

## 受け入れ条件
何ができたら終わりか

## 注意
やってはいけないこと（削除するな、自動化するな、過剰設計に倒れるな）
```

`direction` にも `approach` / `acceptance` / `next` を入れる。起票先の Object は内容で選ぶ（UI 品質 / 基盤・品質 / Agent Ops / Strategy 深化 など、盤面の既存 Object から）。

## SITREP と AAR

**SITREP** は毎サイクル、Campaign のコメントに出す。作戦の状況が前半、`--- Friction 運用所見 ---` 以下が後半。**ユーザーは Campaign を見ているだけで全体が追える**のが狙い。`mentions` に判断を仰ぐ user の uuid を入れる（入れないと誰の Inbox にも届かない）。

**AAR** は演習の終わりに1本。作戦の結果、所見の一覧（実装まで到達したもの / 盤面に残したもの）、**分かったことの類型化**、そして**次の演習が狙うべき類型**を書く。次の演習の設計はここから始まる。

## セッションをまたいで続ける

**演習の状態は盤面にある。** このファイルにも、どのセッションの記憶にも無い。だから途中で切れても拾える。

再開の手順:

```sql
-- ① 走っている演習を見つける（description に【架空演習】と書いてある）
select id, name, identifier, description
from domains where description like '%架空演習%' order by created_at desc;

-- ② その演習の Campaign。scope の domain_ids に ① の id が入っている
select id, name, description from strategies order by created_at desc;

-- ③ 最後の SITREP。どのサイクルまで進んだか・何を観察済みか・何を起票済みかが全部ここにある
--    （Campaign は複数あるので strategy_id で必ず絞る。名前での like は Friction 自身の
--     Campaign を拾ってしまい、演習の続きではないものを読むことになる）
select author_name, content, created_at from strategy_comments
where strategy_id = '<② の id>' order by created_at desc limit 3;

-- ④ 作戦の現在地
select e.display_id, e.title, e.status, e.progress, p.name as phase
from elements e
join objects o on o.id = e.object_id
left join phases p on p.id = e.phase_id
where o.domain_id = '<① の id>' order by e.display_id;
```

**最後の SITREP を読めば、どのサイクルまで進んだか・何を観察済みか・何を起票済みかが分かる。** 続きから回す。AAR が出ていれば演習は終わっているので、AAR が名指しした類型で次の演習を設計する。

演習が1つも無ければ、直近の AAR を探す。それも無ければ、盤面の未着手 Element を眺めて痛そうな類型を1つ選び、そこを突く演習を設計する。

## 規律

このループを壊す失敗が実際に起きたので、規則にしてある。

- **確かめられることを推測しない。** このセッションで同じ形の誤りを3回した。自分が入れた宣言リストを読まずに「検査に穴がある」と断じ、MCP が Unauthorized だったことを「migration を当てる手段が無い」と取り違え、逆に一度「自動適用されている」と早すぎる結論を出した。**最初に触った道具の反応は、システムの性質ではない。** 数える・引く・実際に流す手段があるなら、そうする
- **間違えたら盤面に証拠つきで訂正を書く。** 取り消して黙らない。SITREP に誤りを書いたなら訂正の SITREP を出す。**次のセッションが読むのは盤面であって、こちらの反省ではない**
- **実装を委任するときは「既存の設計意図を先に読め」をブリーフに書く。** 書けばエージェントは読む。読んだ結果「既にある」が4回見つかった
- **委任先が申告した妥協と推測を、そのまま盤面に残す。** 「ここは記述が不足していたので自分で判断した」はブリーフ品質の検証データであり、隠すと次の委任も同じ穴を踏む
- **止まらない。** 判断が要るものはユーザーに上げつつ、それを要さない Element を先に消化する。ブロッカー自体も Element として起票して、盤面から消えないようにする

## 実装との接続

起票された Element を実際に作るのは friction スキルの領分。演習側は**作らない** —— 観察して起票するところまで。ただし演習を回している同じセッションが実装まで進めてよく、その場合は friction スキルの規約（1 Element = 1 branch = 1 PR、レビューゲート、盤面への書き戻し）に従う。

**演習で作ったデータは消さない。** 次の演習との比較材料であり、AAR の根拠でもある。
